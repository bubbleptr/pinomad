# ADR-0011：用结构化提问取代审批

- 状态：Accepted
- 日期：2026-10-07

## 背景

ADR-0005 用 `pinomad.approval` 验证了"需要多端安全的交互用文档实现"，ADR-0006 把"可选的审批闸门（拦在 bash / write / edit 之前）"留到以后。实际用下来，coding agent 的主流用法已经是不审批、直接执行（yolo）：逐条批准命令打断太多，用户也很少真的去读每条命令。真正需要停下来等用户的，是 agent 拿不准方向的时候，比如有几种实现方式、需求有歧义、要不要动某个模块。这时有用的是问用户一个带选项的问题，而不是让用户批准或拒绝一条命令。

批准或拒绝本身就是只有两个选项的提问。保留两套机制，功能重叠，界面上也多一种卡片。

## 决策

1. **不做审批闸门。** 工具继续默认直接执行。roadmap 里的审批闸门去掉；ADR-0008 里"按设备的审批策略"以后如果还需要，再单独决定。

2. **agent 用 `ask_user_question` 工具向用户提问，工具阻塞到用户回答为止。**
   - 一次 1 到 4 个问题。每个问题有问题文本、一个简短标题、2 到 4 个选项（选项有标签和可选的说明），可以设成多选。
   - 客户端给每个问题自动加一个"其他"，可以自由输入。agent 不需要自己写这个选项。
   - 用户可以只回答部分问题，没答的记为跳过。一次提交全部答案。
   - 回答以文本交还给模型：每个问题选了什么、自由输入了什么、或者被跳过。

3. **机制沿用审批的做法**（ADR-0005 验证结果里记下的那套）：
   - 问题和答案都存在对话级文档里，展示类型是新的 `pinomad.question`，宿主重启后各客户端看到的仍是同一份状态。
   - 工具创建一个归它所有的子任务等待答案；中止对话时由子任务的 abort 处理器把问题记为已取消。工具按 `callId` 去重，声明为可以安全重放。
   - 回答由核心实现：网关对照 `pinomad.question` 的 schema 在一个事务里写入答案，以先写入者为准。

4. **问题还没答时，用户直接在输入框发消息，就跳过这些问题。** 网关先把这条对话里未回答的问题记为"用户改为在对话里回复"，工具随之结束，告诉模型去看用户的下一条消息；然后把这条消息作为 steer 提交，不管客户端选的是 steer 还是 follow-up。输入框永远不会被问题卡住。

5. **删除 `request_approval` 工具和 `pinomad.approval` 展示类型**，以及网关的 `decide` 调用。旧数据目录里已有的审批文档按兜底渲染显示。协议去掉了一个调用，属于破坏性变更，协议版本号加一（ADR-0009）。

## 考虑过的方案

- **保留审批，另加提问**：两个工具功能重叠，模型要判断该用哪个，界面上也多一种卡片。审批能做的，提问都能做。
- **可选的审批闸门**：要做规则配置（哪些命令要批、哪些放行），而且每次拦截都要人在场。在 yolo 用法下没人想开，就先不做。
- **用户发的消息直接当作回答**：只有一个问题时很自然，多个问题时不知道对应哪一题。跳过问题、让模型自己读消息，语义更清楚。
- **问题没答完时禁用输入框**：用户想说"先别管这个，改做别的"时只能先中止，体验更差。
- **单题提问**：结构更简单，但要对齐好几件事时会反复打断用户。

## 后果

- 去掉审批以后，agent 在宿主上执行的每条命令都不经过用户。宿主的安全边界仍然是"只有配对设备能连上"（ADR-0008），加上 worktree 隔离对话之间的文件（ADR-0010）。
- 问题等待时，用户必须打开对话才看得到。对话列表的提示和推送通知留到 ADR-0008 第三期一起考虑。
- ADR-0005 里审批相关的验证结果仍然成立，只是展示类型从 `pinomad.approval` 换成了 `pinomad.question`。
