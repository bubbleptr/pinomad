# ADR-0004：先内置后开放的插件策略

- 状态：Accepted
- 日期：2026-10-04

## 背景

ADR-0001 不再兼容 CLI 插件，但 PiNomad 迟早需要扩展机制。插件协议如果在产品定型前就对外公开，就等于过早承诺一套 API：此后每次调整交互都要背着兼容性走，而且上游 Durable 自己也还是 Experimental。

## 决策

1. 早期所有功能由 PiNomad 自己实现，不公开插件协议。
2. **内置功能也按插件边界来写**：每个功能都是一个独立的 Durable 扩展（`defineExtension`），自带它的文档定义和工具。核心只认识扩展注册表和展示类型（ADR-0005），不 import 任何具体功能的内部实现，并用依赖规则把这条边界卡死。这样 PiNomad 自己就是协议的第一个用户。
3. 主动接入两个现成的外部标准作为早期的外部扩展入口：**MCP** 和 **Skills**（Markdown 技能，加上 `AGENTS.md`）。接入它们是 PiNomad 自己的选择，不代表兼容 CLI。
4. 插件不能自带 React 或原生 UI 组件。插件只通过结构化数据（Durable 文档、工具结果的 `details`）和 service 方法暴露状态与操作，界面由 PiNomad 渲染。
5. 满足以下三个条件时才公开插件协议：
   - 至少 3 个内置功能在用同一套展示类型；
   - 这套类型连续几个版本没有破坏性变更；
   - 确实有外部需求，而且 MCP 满足不了，比如需要自定义界面状态或交互。

   公开之后，贡献者必须按 PiNomad 的协议写插件。

## 后果

- 协议按层次分批开放：
  - 工具、钩子、提示词片段属于上游的 Durable 扩展 API，本身就是公开的，不需要拦；只返回文本的工具靠兜底渲染也能用。
  - 展示类型和交互约定属于 PiNomad，先内部使用，稳定后再公开。
  - 插件的打包、分发、信任和沙箱成本最高，最后做。
- 把内置功能写成扩展会比直接写进核心多一层间接，这是为以后开放协议预付的成本。
