# ADR-0034：提交的送达状态与断线恢复

- 状态：Accepted
- 日期：2026-10-28
- 补充 ADR-0018 §2（同一主版本内新增调用和可选字段）、ADR-0024 §3（断线时不重放已发出的调用）和 ADR-0033 §5（交接后已发出的调用不重放）；为 `submit` 明确一个范围很窄的恢复例外。

## 背景

用户发出消息后，要等宿主写入 `pi.user` 条目、快照回到客户端，气泡才会出现；发送中和排队中没有可显示的本地状态。`submit` 在 TS 和 Rust 控制器里都是 command 类，结果被丢掉，失败只变成一条 notice。连接断开时，已经发出但没等到结果的提交既不能确认送达，也不能安全重发：重发可能再执行一遍宿主的预处理，不重发则可能悄悄丢消息。

`requestId` 是按对话持久化的幂等键，但 pi-durable 的去重在宿主的图片 ref 解析、附件标记、skill 展开和 `dismissPendingQuestions` **之后**才发生。同一个 `requestId` 重发会再次关掉新出现的问题、再次展开 skill，并可能因为图片 ref 已经不再展示而报错。宿主也**不保证**准入产生的 ops 帧先于 result 帧发出，客户端不能靠“先收到哪个帧”判断是否已经准入。

只靠重发无法区分“宿主没收到”和“宿主收到但回复丢了”。快照和 ops 也没有 `requestId` 到条目的对应关系，不能按请求身份对账。因此需要一个只读查询，和一个把去重提前到副作用之前的宿主行为。

ADR-0024 §3 规定断线时已发出、未回结果的调用全部失败且不自动重发；ADR-0033 §5 也规定交接后不重放。那条规则保护的是命令的顺序和副作用，但 `submit` 如果照做，客户端只能在“可能重复”和“可能丢失”之间二选一。这个例外必须只覆盖 `submit`，并且先查询再决定是否重发。

## 决策

1. **新增只读调用 `submission`（协议 5.25）。** 参数是 `{ conversationId, requestId }`，返回 `{ submissionId, status: "queued" | "placed" | "done" | "unanswered", entry?: number } | null`。它直接读 storage 的请求索引，不经过 submit 预处理，也不产生任何副作用；不存在的记录返回 `null`。它不是流，也不进命令队列，状态变化仍由快照和 ops 送达。

2. **宿主在处理 submit 时先按 `requestId` 去重，再做预处理。** 已存在的记录直接返回 `submissionId` 和记录中已有的 `entry`，不再解析图片 ref、标记附件、展开 skill 或关闭待答问题。同一对话、同一 `requestId` 的 submit 在宿主里按 `(harness, conversationId, requestId)` 串行：第二个等第一个的**准入**结束，再重新查记录；它不等整轮运行结束，否则同一对话后面的消息会全部排队在一个答案后面。

3. **submit 结果新增可选字段 `entry?: number`。** 准入成功后读一次记录，记录有 `entry` 就带上，没有就不带；判断依据是记录本身，不是 `status`。准入已经持久化后，这次读取失败只表示结果不带 `entry`，不能把提交改成 `ok:false`：`ok:false` 只用于准入**之前**的拒绝（参数、图片 ref、附件、skill、会话不存在等）。

4. **版本按 ADR-0018 只增不删。** `PROTOCOL` 升 minor，`CALL_SINCE.submission = 25`，`FEATURE_SINCE.submitEntry = 25`；`CALL_SINCE.submit` 保持 0。旧宿主不认识 `submission` 时回 unsupported；旧客户端忽略新调用和 `entry`。客户端判断 `entry` 是否可用要看宿主 minor（`submitEntry`），不能看结果里有没有这个字段——新宿主的排队结果本来就没有。

5. **客户端为每次发送保留一个逻辑提交。** 调用方生成 `requestId`，控制器的逻辑提交记录 `{ requestId, conversationId, content, whenBusy, placement, phase }`。`conversationId` 在执行时解析一次并固定，之后的重试不再读“当前对话”。`phase` 分为客户端队列里的 queued、已发出未回结果的 inFlight、结果不明的 unknown、明确失败的 failed 和已有宿主事实的 settled。

6. **重连并完成同步后，先对账再放行后续命令。** 按原顺序处理 `unknown` 的逻辑提交：用 `submission` 查询；查到记录就按 `requestId` / `submissionId` / `entry` 对账，不按文字匹配；只有 `null` 才用同一个 `requestId`、同一个 `conversationId` 重发。恢复期间后续命令等待，保证不越序，也不发到别的对话。这是 ADR-0024 §3 和 ADR-0033 §5 的一个明确例外：只限 `submit`，只限同一个 `requestId` 和固定对话，只在同步完成后发生。

7. **超时只改变显示，不等于失败。** 30 秒没有结果就把 inFlight 标成 unknown（“未确认”），保留重试入口；重试先查询，查不到才重发。只有宿主明确拒绝才是 failed；编辑只对 failed 和查询确认未准入的项开放。排队记录被消费、被撤回或被 reset 裁掉时，按 `submission` 的终态对账并移除本地项，不用文字猜。

8. **允许短暂的可见重复。** result 到达之前，本地项和宿主刚写入的真实气泡可能同时存在；两个帧之间只差宿主侧的处理时间。之后以宿主事实为准，不允许持久重复。要做到零重复，需要让快照本身携带 `requestId` 和条目的对应关系，那要改 pi-durable，不在本决策内。

## 考虑过的方案

- **只靠宿主现有的 `requestId` 去重，不加重发前的查询**：能防重复准入，但重发仍会再次执行预处理；客户端也无法区分“没收到”和“收到但没回结果”。不取。
- **submit 直接返回完整记录**：客户端一次就能拿到状态和 entry，但会把 pi-durable 的内部记录形状搬上线上，提交结果也不再是“准入回执”这一件事。查询只暴露对账需要的四个状态和一个 entry，边界更小。
- **保证准入的 ops 先于 result 发出**：客户端仍然无法在断线时判断是否送达，且需要改 pi-durable 的发送顺序。恢复问题没有解决。
- **重连时重放所有在途调用**：会破坏命令顺序和工具副作用；ADR-0024/0033 明确不这样做。例外只给 `submit`，而且必须先查询。
- **把 30 秒超时当失败，允许直接编辑重发**：超时只是客户端没等到结果，宿主可能已经排队或写入。直接重发会重复执行；因此引入“未确认”，编辑也受查询约束。
- **让快照携带 requestId 来消除短暂重复**：需要改上游的条目和 delta 格式，收益只是去掉一个很短的重复窗口，不取。

## 后果

- 宿主多一张按对话和 `requestId` 索引的准入队列；只在准入期间串行，不阻塞运行和其他对话，结束后清理。
- 旧宿主没有 `submission` 也没有 `entry`，客户端按现有行为退化为“没有本地送达状态”；旧客户端忽略新调用和字段，新宿主照常工作。
- 准入后读记录失败时，客户端先拿到 submissionId，随后用快照或 `submission` 补上 `entry`，不会把成功的提交误报为失败。
- `submission` 只按已知对话和精确的幂等键读取，不遍历对话内容，也没有超出 `submit` 已有权限的新数据出口。
- 提交在客户端被杀掉后仍然丢失（逻辑提交不持久化），和现在一样；本决策不承诺跨进程 exactly-once。
- Web 和桌面端先接入这套对账；iOS 在接入前保持现有行为（出错恢复草稿、不保留本地项），避免同一条消息出现两份可重发的副本。
- 时序行为必须用确定性事件序列验证，覆盖重复 `requestId` 不再执行预处理、并发只准入一次、四种查询状态和准入后读失败；协议快照只应新增，Rust 对照向量随之重新生成。
