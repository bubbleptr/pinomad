# ADR-0037：账号设备——服务端记下经账号加入的设备，可以一键从所有宿主上踢掉

- 状态：Accepted
- 日期：2026-10-31
- 补充 ADR-0022 §6（服务端可以请宿主吊销，宿主照旧是最终裁决的一方）和"后果"里的"账号层面一键把某台设备从所有宿主上踢掉"

## 背景

设备登记和吊销按宿主分别管（ADR-0022 §6），丢了手机要逐台宿主去吊销。官方服务端对外开放后，这是用户找得到的唯一入口；TestFlight 外部测试（#440）也要在审核结束后把审核员手机上用过的设备踢掉。

服务端现在不知道哪台设备进了哪台宿主：它替登录会话向宿主要一份邀请（ADR-0022 §4），把配对密钥转给设备，之后的 IK 配对在设备和宿主之间完成，结果不回到服务端。设备给每台宿主各生成一把密钥（ADR-0035），服务端也没有能跨宿主认出同一台设备的东西。登录会话不能充当这个东西：改密码（#477）和"退出所有会话"会删掉别的会话，而丢了手机正是要改密码的时候。

## 决策

1. **账号设备是服务端上独立于登录会话的一条记录。** 客户端在本机第一次登录前生成一个随机的设备 ID（128 位，base64url），存在本机，之后每次登录都带上：`POST /api/login` 的请求体加可选的 `device: { id, name }`。服务端按 `(账号, 设备 ID)` 找到或新建一条账号设备，登录会话指向它。不带 `device` 的老客户端每次登录得到一条新的账号设备，名字未知。设备 ID 只是账号内部的标签，不是凭据：它由客户端声称，只在已经用密码登录的账号里有意义。升级前已有的登录会话各补一条名字未知的账号设备。

2. **宿主告诉服务端哪把公钥是经它担保进来的。** 宿主为 `pairing-request` 签发的邀请记下 `requestId`；设备用这份邀请登记成功后，宿主经控制连接发 `device-admitted { requestId, publicKey }`。服务端在发出邀请时就记下 `(requestId, 账号设备, 宿主)`，收到报告后补上公钥；只核对 `requestId` 是发给这台宿主的、同一份邀请只报告一次、没有过期太久（邀请到期后再留一天宽限，接住断线期间缓冲的报告）。过了宽限都没报告的记录顺手清掉。控制连接断着时，宿主把报告留在内存里（最近 64 条），下次声明了 `device-reports` 的 `registered` 后补发；宿主重启前没发出去的就丢了，这台设备在这台宿主上只能去宿主上吊销。报告到达时这台账号设备已经被踢掉（拿着邀请的设备正好在被踢时加入），服务端当场为这把公钥写待吊销记录并发给宿主。

3. **踢掉 = 服务端不再为它担保 + 请所有宿主吊销。** `POST /api/devices/:id/kick` 要求重新输入密码（和删除账号一样，防止拿着别人手机上的会话踢掉主人的其他设备）。服务端在一个事务里：删掉这台账号设备的所有登录会话，标记已踢掉，为它在每台宿主上登记过的每把公钥写一条待吊销记录。在线的宿主立刻收到 `revoke-device { publicKey }`，宿主走现有的 `revokeDevice`（写入吊销表、断开这台设备的连接），回 `device-revoked { publicKey }`，服务端收到才删待吊销记录；离线的宿主在下次 `registered` 后收到。不能踢当前这台设备，那是退出登录。

4. **宿主仍然是最终裁决的一方。** 服务端只能请求吊销。宿主照旧可以重新扫码配对被踢掉的设备（ADR-0022 §6），服务端不会再去撤销。被踢掉的设备重新用密码登录，账号设备恢复成正常状态；它在宿主上的旧公钥已经吊销，经账号担保回不去，要在宿主上扫码，或者用新身份重新加入。

5. **兼容（ADR-0018）。** 新帧放在 feature 后面：宿主在 `register` 的 `features` 里声明 `device-reports`，服务端在 `registered` 的 `features` 里声明同一个字符串，双方都声明了才发这三种帧（老的一方解码器遇到不认识的帧会断开）。老宿主上没有报告，账号页里这台宿主显示"在宿主上吊销"：服务端在每次登记时记下宿主有没有声明 `device-reports`，`GET /api/hosts` 的 `deviceReports` 字段给出最近一次的结果，宿主离线时也能判断。登录请求里的 `device` 是可选字段，老服务端忽略它。

6. **账号页列出账号设备。** `GET /api/devices` 返回每台账号设备的名字、首次登录和最近登录时间、是否当前设备、是否已踢掉，以及它经账号进过的宿主和每台的状态（已登记 / 等宿主吊销 / 已吊销）。只列有过登录的设备；扫码配对、从没登录过账号的设备不在里面，照旧只能在宿主上管。同一台设备在一台宿主上有过几把公钥（被吊销后换新身份重新加入）时，这台宿主只列一行，取最好的状态（已登记 > 等宿主吊销 > 已吊销）。不带设备 ID 的老客户端每次登录多一条名字未知的记录，没有有效会话、也没有任何担保记录的会在下次这样登录时清掉。

## 考虑过的方案

- **登录会话就是设备**：不用改客户端，服务端已经知道哪个会话要了哪份邀请。但改密码、"退出所有会话"、会话 30 天到期都会让设备从列表里消失，丢手机后改密码的人就再也找不到它。
- **服务端存配对密钥的哈希，宿主另存"邀请哈希 → 公钥"**：不用新加宿主到服务端的报告帧。但宿主要多一份持久文档，服务端也分不清哪些邀请真的用掉了，列表里会混进过期没用的邀请。
- **服务端直接吊销，不经宿主**：服务端没有宿主的设备表，也不该有（ADR-0022 §6）；而且直连的设备根本不经过服务端。
- **设备向服务端报告自己在每台宿主上的公钥**：不用改宿主，但这是设备的一面之词，被盗的设备可以不报或者乱报；宿主报告的才是真正登记进去的那把。

## 后果

- 服务端多存：账号设备（客户端声称的 ID、名字、首次和最近登录时间）、每台设备在每台宿主上的公钥、待吊销记录。删除账号时一起删掉（级联），宿主退出账号时删掉这台宿主的记录。隐私政策（#455）要写上。
- 控制连接的帧不在宿主和客户端之间的协议里，靠 feature 协商，不升 `PROTOCOL`。`packages/client` 的登录请求变了，同步 `crates/pinomad-core` 并重新生成对照向量。
- 本 ADR 生效前就配对好的设备，服务端没有它们的公钥，只能去宿主上吊销。#440 的审核员手机要在这之后再登录、加入宿主。
- 分 PR：服务端和宿主（本 ADR、表、帧、接口），Web 账号页，iOS 登录带设备 ID 和账号页。
