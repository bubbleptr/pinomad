# ADR-0001：PiNomad 拥有 UI 契约，不做 Pi CLI 的兼容层

- 状态：Accepted
- 日期：2026-10-04
- 来源：Pace（`bubbleptr/PiGUI` @ 2315db6）转向讨论

## 背景

Pace 的定位是 Pi Coding Agent CLI 的图形界面：扩展生态、会话格式（`~/.pi` 下的 JSONL）、交互模型都由 CLI 决定，Pace 只做投影。这条路在结构上走不通：

- 三方扩展的 UI 契约由 TUI 定义。`ctx.ui` 接收的是终端组件工厂，`select` / `confirm` / `input` 是单进程、单界面的阻塞对话框，GUI 拿不到可以重新渲染的数据。
- 适配成本没有上限：插件数量会持续增长，每个插件的界面都要单独适配，工程量不收敛。
- 产品目标是桌面、Web、移动端多端一致，一个由外部作者随意定义界面的生态与这个目标直接冲突。

Pace 至今没有接上 `uiContext`，Dock 也只有固定面板，这是定位导致的结果，不是进度问题。

## 决策

1. PiNomad 是独立产品，定义并拥有自己的 UI 契约。插件和外部能力（MCP、Skills、工具）由 PiNomad 选择接入、规定接入方式。
2. 不兼容 Pi CLI 的扩展、配置和会话格式。旧 Pi JSONL 会话和 Pace 的会话数据不导入，也不保留只读入口。
3. PiNomad 放在新仓库开发，使用新的 app ID、更新通道和数据目录。Pace 留在原仓库进入维护模式，只做 Pi 升级、bug 修复和安全修复。
4. 从 Pace 按需复制代码（UI 组件、工作区能力、Electron 外壳、发布脚本），不整体 fork；复制时在提交信息里注明来源 commit。两个仓库之间暂不抽共享包。

## 考虑过的方案

- **继续兼容 CLI 插件**：能复用生态里不碰界面的部分（工具、斜杠命令、Skills），但体验层无法保证，见背景。
- **在 Pace 仓库里改造，或者另建 `apps/<new>`**：两套互相矛盾的架构原则（"Pace 是 Pi 事件的投影" vs "产品拥有 Harness"）会同时出现在 README、ADR 和 CONTEXT.md 里，持续误导 agent；原地改造还会把半成品推给现有用户的应用内更新。
- **按会话选择引擎、两套运行时并存**：作为 Pace 的过渡方案可行，但它的前提是保留 CLI 互通，与第 1 条冲突。

## 后果

- Pace 用户迁移到 PiNomad 时，历史会话无法带过去。
- 第一方能力（grep/find/ls、读图片、MCP 桥接、子代理、diff 审阅等）都要自己实现或接入，没有现成生态可用。
- 插件策略见 ADR-0004。
