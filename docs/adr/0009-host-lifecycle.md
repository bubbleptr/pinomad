# ADR-0009：宿主生命周期——用户级系统服务、源码检出升级、等空闲重启

- 状态：Accepted（§2 安装方式、§6 升级命令由 ADR-0016 修订：分发改为单个 npm 包，打包安装升级走 `npm i -g`；源码检出仍是开发路径；§8 的严格相等由 ADR-0018 修订为主次版本号；本文其余部分不变）
- 日期：2026-10-06

## 背景

ADR-0003 和 ADR-0008 都把"宿主谁启动、怎么常驻、崩溃后谁拉起、怎么升级"留到了这里。远程访问第一期做完以后，这是在外面用手机连宿主的前提：宿主进程没了，手机上什么都做不了。

现状：

- 宿主只能在终端里手动起（`bun run host` 或 `bun run start`），终端关掉宿主就退出，机器重启后也不会自己起来。
- 安装方式就是源码检出：`git clone` 加 `bun install`，宿主用 Node 直接跑 `apps/host/src/main.ts`（依赖 `node:sqlite` 和 Node 原生的 TS 类型剥离）。
- 本机浏览器用的 Web 客户端由 Vite 开发服务器在 5199 端口提供。构建好的 `apps/web/dist` 只在远程端口上提供。
- 崩溃恢复已经有了：Durable 从检查点继续，`harness.resume()` 在启动时续跑未完成的工作。被杀掉的宿主留下的目录锁，下一个宿主会在过期窗口内重试拿到（`proper-lockfile`，默认 10 秒过期，重试覆盖这个窗口）。
- 一次中断对正在跑的工作的影响取决于工具：声明了 `replay: "safe"` 的工具会重跑；bash、write、edit 不会重跑，模型拿到一个"已中断、可能执行了一部分"的错误结果。宿主正常关闭时不写结果，正在跑的 turn 下次启动时接着跑。

## 决策

1. **宿主作为当前用户的系统服务常驻，由操作系统的服务管理器负责开机启动和崩溃拉起。** 宿主本身就是常驻进程；由服务管理器托管时，它不自己脱离终端（不 fork 出子进程后自己退出），不写 PID 文件，日志写到标准输出。第一期不提供自己脱离的 `--detach` 模式，也不实现 PiNomad 自己的监管进程。开发调试仍然在终端里直接跑 `bun run host` 或 `bun run start`，进程占住终端，Ctrl-C 即停。
   - macOS：`~/Library/LaunchAgents/` 下的 LaunchAgent，`KeepAlive` 加 `RunAtLoad`。
   - Linux：systemd 用户单元 `~/.config/systemd/user/pinomad.service`，`Restart=on-failure`。要在用户没登录时也运行，需要 `loginctl enable-linger`，安装命令检测到没开时提示用户。
   - 以当前用户身份运行，不用 root：agent 要用的是这个用户的 shell、代码仓库和 `~/.pi/agent` 下的认证。
   - Windows 不在范围内。

2. **安装就是源码检出，第一期不做 npm 包。** 升级就是更新检出再重启服务。打包发布要额外处理一个限制：Node 不对 `node_modules` 里的文件做类型剥离，宿主必须先构建成 JS。这件事留到以后单独决定。

3. **用一个服务命令管理宿主**：`bun run service -- <子命令>`。
   - `install [宿主参数…]`：生成并加载服务定义，然后启动服务。宿主参数（`--data-dir`、`--remote-port`、`--public-url`、`--project` 等）原样写进服务定义。改参数就是带着新参数再跑一次 `install`。不另设配置文件，PiNomad 要不要有自己的设置文件仍然按 ADR-0006 留到做设置界面时决定。
   - `uninstall`：停止服务，删除服务定义。不删数据目录。
   - `status`：服务管理器里的状态，加上用 token 连宿主得到的结果（能否连上、当前检出的 commit、有没有运行中的任务）。
   - `restart [--force]`：见第 5 条。
   - `logs`：显示宿主日志的末尾（macOS 读日志文件，Linux 调 `journalctl --user -u pinomad`）。

4. **服务定义在安装时固定运行环境**，因为服务管理器给的环境和用户终端里的不一样：
   - 可执行文件用安装时的 `process.execPath` 的绝对路径。nvm、fnm 装的 Node 不在服务的 PATH 里，而宿主需要 Node 25 以上。
   - **PATH 用安装时终端里的值。** agent 的 bash 工具继承宿主进程的环境，launchd 默认给的 PATH 里没有 Homebrew、语言版本管理器这些目录，agent 在里面跑命令会找不到工具。终端里装了新工具、PATH 变了以后，重新 `install` 一次即可刷新。
   - 工作目录设为用户主目录。宿主用 `SettingsManager.create(process.cwd())` 读 pi 的设置，会顺带读 cwd 下的 `.pi/settings.json`，不能让它跟着仓库目录走。
   - `PINOMAD_DATA_DIR` 在安装时展开成显式的 `--data-dir`，服务定义里不依赖环境变量。

5. **重启和升级默认等到空闲，`--force` 立即执行。**
   - `restart` 先用 token 连上宿主，读任务图。有未结束的任务时，列出这些任务所在的对话，等它们全部结束再重启；等待期间可以 Ctrl-C 取消。`--force` 不等，直接重启，交给 Durable 恢复，bash 这类工具按上面说的以中断结束。
   - 宿主连不上（没在运行，或已经崩了）时直接重启。
   - 等待中的审批（`approval.wait`）也算未结束。要不要等它，由用户决定是否加 `--force`。
   - 从检查完空闲到真正停掉宿主之间，有新提交进来的话会被这次重启打断。窗口很小，我们接受这个代价，不在网关里加"排空"状态。
   - 重启本身交给服务管理器：`launchctl kickstart -k gui/<uid>/<label>`，`systemctl --user restart pinomad`。

6. **升级命令**：`bun run upgrade [--force]`，依次执行 `git pull --ff-only`、`bun install`、`bun run build`，最后做一次第 5 条的 `restart`（`--force` 透传）。前面任何一步失败都直接停下，不重启，服务继续跑旧代码。工作区有未提交的改动时拒绝执行。

7. **服务模式下由宿主自己提供 Web 客户端。** 服务模式下没有 Vite 开发服务器，所以本机回环端口也用 HTTP 提供构建好的 `apps/web/dist`（和远程端口用同一份文件），这个端口自己的 origin 自动加进允许列表。`bun run link` 打印的链接在 Web 客户端由宿主提供时指向宿主端口，不再固定指向 5199。`bun run start` 和 Vite 继续作为开发方式保留。

8. **协议版本检查。** 升级后，手机上已经打开的页面还在跑旧版本的 Web 客户端，重连时可能和新宿主的协议对不上。`packages/protocol` 里定义一个整数协议版本，有破坏性变更时加一。宿主在 hello 帧里带上它，客户端和自己编译进去的版本比较：
   - 一致：照常使用。
   - 不一致：如果页面是宿主提供的，自动刷新一次去加载新版本；否则（Vite 开发服务器、以后的原生 App）显示"宿主版本不匹配"，不再发送调用。

9. **日志**：宿主的标准输出和标准错误交给服务管理器。macOS 写到 `<数据目录>/logs/host.log`，Linux 进 journald。宿主的日志只有 ready 行和警告，从不包含 token 等凭证（这条约束不变）。

## 考虑过的方案

- **pm2 / forever 这类进程管理器**：要额外装一个全局包，它自己也要靠系统服务来开机启动，最后还是落到第 1 条。
- **宿主在服务模式下自己脱离终端**：服务管理器会把"拉起的进程退出了"当成崩溃，反复重启；PID 文件、日志重定向也都是服务管理器已经做好的事。不采用。
- **可选的 `--detach`**：不装服务、只想临时把宿主放到后台时有用，默认仍不脱离，服务定义里也从不带它。第一期用 `nohup` 或 tmux 就能覆盖，以后有需要再加；停止宿主可以复用 token 连接加一个 shutdown 调用，单实例由目录锁保证。
- **PiNomad 自己的监管进程**（一个长期存活的薄进程守住连接，宿主作为它下面可以替换的工作进程）：第一期不做。以后满足任一条件时重新考虑：中继（ADR-0008 第二期）要求升级时设备不断连；需要失败自动回滚的升级；要支持没有服务管理器的平台。即使做了，监管进程本身仍然装成系统服务。
- **macOS 上用 LaunchDaemon（加 `UserName`）**：不用登录就能在开机时运行，但安装要 sudo，系统域的服务也拿不到用户会话（钥匙串、用户级代理设置）。不登录的 Mac mini 打开自动登录就能满足需求，第一期不做。
- **桌面端内嵌宿主**：违背 ADR-0003"桌面端也是客户端"。以后桌面端可以替用户执行 `service install`，但宿主仍然是独立进程。
- **重启前排空（拒绝新提交，等运行中的 turn 结束）**：体验最好，但网关要多一个状态，各客户端也要能显示这个状态。对自用的宿主来说，等空闲加一个小竞态窗口已经够用。
- **服务启动时通过登录 shell（`zsh -lc`）拿 PATH**：环境总是最新的，但会执行用户 shell 配置里的所有内容（交互提示、慢的插件、只在交互模式下才对的东西），出了问题服务起不来，也很难排查。安装时固定下来更容易预期。

## 后果

- 服务模式下 `bun run start` 会因为目录锁拿不到而失败，这是预期行为：同一数据目录只有一个宿主（ADR-0002）。开发时用另一个 `--data-dir`，或者先 `uninstall` 服务。
- 源码检出就是安装：用户机器上需要 Bun 和 Node 25 以上，检出目录不能随便移动或删除（服务定义里记的是绝对路径，移动后要重新 `install`）。
- 宿主因为配置错误一启动就退出时（比如数据目录被另一个进程锁住），服务管理器会不断重启它。launchd 有 10 秒的默认节流，systemd 有启动次数限制，不会忙等，但 `status` 和 `logs` 要能让用户看出原因。
- macOS 上 launchd 不轮转日志文件。宿主日志很少，第一期不处理轮转。
- 机器睡眠时宿主不可达。Mac mini 等作为宿主的机器要用户自己在系统设置里关掉睡眠，PiNomad 不替用户改电源设置。
- 协议版本号要靠人在破坏性变更时记得加一，没有机器检查。
