# ADR-0020：桌面端以已配对设备连接宿主，回环端口也接受安全通道

- 状态：Accepted
- 日期：2026-10-10

## 背景

ADR-0017 定了桌面端用 Electron，页面打包进 App，私钥放进钥匙串，能连多台宿主。

现状：宿主默认只监听回环地址，回环端口只认 token（ADR-0008 §7）。token 是数据目录里的一个全权限共享密钥，浏览器连接时还要校验 Origin 白名单。宿主密钥、配对邀请和安全通道，只有开了 `--remote-port` 或 `--relay` 才存在；两样都没开时，`createPairing` 直接失败。

最常见的用法是在 Mac 本机跑宿主。照现在的规则，桌面端连本机宿主只能去读 token。

## 决策

1. **桌面端连任何宿主，包括本机的，都作为已配对的设备走安全通道，不读 token。** 设备私钥由 main 进程用 `safeStorage` 加密后存在 userData 里，每台宿主一条。
2. **回环监听在 `/secure` 路径上也接受安全通道**，复用远程监听的握手和设备登记。其他路径照旧只认 token，并校验 Origin。安全通道不校验 Origin，认证靠 Noise 握手。这是对 ADR-0008 §7 的补充：回环地址上 token 和安全通道并存，非回环地址仍然只接受安全通道。
3. **宿主总是加载自己的密钥，并能签发配对邀请**，不再只在开了远程访问时才有。密钥在第一次启动时生成。
4. **配对链接选能到达最远的地址**：先中继，其次局域网或用户指定的公网地址，最后回环。回环链接只能在宿主这台机器上用。
5. **桌面端和 npm 包共用版本号和 `v*` tag。** 同一次发布同时产出 npm 包和签名、公证过的 macOS 安装包；自动更新从 GitHub Release 读取。

## 考虑过的方案

- **桌面端读 token**：宿主不用改。但有三个问题：
  - token 是全权限的，桌面端不会出现在设备列表里，也不能单独撤销，把私钥放进钥匙串也就没有意义了。
  - 本机连接和远程连接成了两套机制。
  - 要把 Electron 页面的 Origin 加进白名单。
- **本机也要求开 `--remote-port`**：宿主不用改。但只为了在本机用桌面端，就得在 `0.0.0.0` 上开一个端口，暴露面平白变大。
- **桌面端单独定版本号**：桌面端可以单独发版。但桌面端里的界面就是 npm 包里那份 Web 构建，分开定版本只会多出一个要对照的版本号。真需要时再拆开。

## 后果

- 本机任何程序都能连上回环端口，尝试握手。但没有配对密钥、也没有已登记的私钥，握手过不了；配对密钥只能由已认证的客户端申请。暴露面和局域网监听一样，只是限于本机。
- 即使没开远程访问，数据目录里也会有宿主密钥文件。
- 纯本机的宿主上也能用 `pinomad pair`，打印出来的是回环链接，手机扫了打不开。
- 签名和公证需要在仓库里配置 Apple 证书和公证凭据；每次发布多跑一个 macOS runner 上的 job。
- 桌面端遇到协议主版本不一致，不能靠刷新页面解决（ADR-0018）：客户端旧了，走自动更新；宿主旧了，提示运行 `pinomad upgrade`。
