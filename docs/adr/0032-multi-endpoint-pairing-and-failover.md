# ADR-0032：远程多候选——配对、重连与故障回退

- 状态：Accepted（P2P 传输与信令连接由 ADR-0033 补充）
- 日期：2026-10-25
- 补全 ADR-0015 后果中的单地址二维码和 ADR-0020 §4（配对链接只选最远地址）；补充 ADR-0018 §4（关闭码规则在多候选下的适用范围）和 ADR-0022 §4（账号 Pair 转发候选）

## 背景

宿主可以同时开远程端口和服务端中继，但配对邀请只带一个地址，而且有中继时优先中继；每个客户端的宿主记录也只保存一个地址。首次连接失败会直接终止 readiness，常规重连只认识同一个地址。于是已经配置好的直连路径不能作为配对或重连候选，一条路径坏掉就可能让整台宿主不可达。

ADR-0015 的后果明确把“二维码里只有一个连接地址，局域网和中继两个候选地址自动选择”留到以后；ADR-0020 §4 的“选能到达最远的地址”也是单地址思路。这份 ADR 决定这个“以后”怎么做，以及它和配对、重连、错误处理、地址变化的关系。

## 决策

1. **配对邀请携带完整候选，不做“先单地址配对、连接后再学习”的半量方案。** 二维码、粘贴链接和账号 Pair 得到同一组候选；旧客户端仍然只读邀请里的 legacy 地址，维持现有单地址行为。服务端只 additive 地转发宿主给出的候选，不持久化 endpoint。

2. **候选只描述传输和路径角色，不出现厂商名。** 当前只有 WebSocket 传输和直连 / 中继两种角色；模型允许 N 条，但当前宿主通常发布一条直连和一条中继。宿主从当前配置生成完整列表，不在 Harness 或 Durable 里另存地址数据库；自动局域网地址在每次邀请和每次安全连接的 hello 时重新探测，不复用监听器启动时的缓存。

3. **Auto 的尝试顺序是：本机 loopback 入口、宿主公布的 relay（保持顺序）、宿主公布的 direct（保持顺序）。** 任意时刻只有一条物理活动连接，串行尝试；本轮不测量延迟、不并行抢连、不做 relay 到 direct 的在线升级、不多路径同时传业务数据。loopback 是 client-local 入口，不属于宿主发布的远程集合；宿主发布、替换或清空远程列表都不能删除它。长期 WebRTC 的并行建连由 #345 另定。

4. **每个候选独立，整轮共享身份。** 同一轮里的候选共享固定 hostKey、设备密钥和配对上下文；message 2 确认前用原 pairing secret 重试，确认后只使用已登记的设备身份。socket open、Noise、业务 hello 和首次必要同步都有有限期限并绑定连接代际；候选退休后，晚到的消息、计时器和配对回调不得影响下一候选。一轮内每个适用候选都有机会，整轮失败才退避；网络变化取消退避并重开一轮。

5. **paired 和 ready 是两个里程碑，分开报告。** paired 是收到并验证 Noise message 2、确认宿主接受了设备；ready 是业务 hello 和首份必要快照已经到齐。账号 Pair 可以在 paired 后关闭 socket，再按保存的记录正常连接；扫码 / 粘贴可以在同一协调器中继续到 ready。paired 后立即独立持久化身份和候选，持久化失败单独报告；持久化或同步失败不能撤销配对、生成新设备密钥或伪装成未配对。

6. **认证边界决定错误作用域。** 裸 WebSocket close（包括 1008、4400、4401）、Noise 认证失败、无效密文和超时都只终止当前候选；单条 relay 的 4401 或 host key 验证失败不得修改固定身份、删除配对记录或阻止健康的 direct。只有经过安全通道验证的业务 hello 宣布协议主版本不兼容才全局终止。平台明确无法使用的候选（例如 HTTPS 页面受 mixed-content 限制不能连远程 ws://）跳过并用于诊断，不伪装成宿主离线。所有适用候选都失败后，才把本轮汇总成用户可见的 unauthorized / pairing failure。

7. **地址变化靠“还有一条活路”更新。** 宿主在每次安全连接的 hello 里发布当前完整远程列表，客户端验证后按 hostKey 更新存储。更新与名称、账号关联、重新配对和忘记宿主共用同一串行读改写队列，只改 endpoint 信息和必要的 legacy 兼容字段，不清空身份、名称、账号或配对时间，也不 resurrect 已忘记的宿主。有效非空列表同时把非 loopback 的 legacy 地址更新为“relay 优先，否则首个 direct”，让旧客户端也有可用地址；loopback 的 legacy 地址保持不变。显式空远程集合清空远程候选但保留本机入口；没有本机入口时后续连接报告“远程访问不可用”，不再永远重试旧地址。

8. **兼容按“不知道就忽略、知道但坏了才拒绝”处理。** 未知 schema、未知 transport、缺少字段都回退到旧行为；当前 schema 下的 malformed 集合在配对时拒绝邀请、在 hello 时保留旧集合且不中断业务连接、在 StoredHost 读取时只丢集合。显式空集合在配对邀请里是 malformed，在 hello 和 StoredHost 里是合法的“清空远程候选”。重复的集合参数在配对邀请里拒绝；完全相同的 entry 按首条去重；同 transport + URL 的角色冲突和超过共享上限是 malformed。生成方不得静默截断。旧记录没有集合时继续只用 legacy 地址；新客户端在集合明确有效（包括空集合）时以集合为准，缺失或不可用时才回退，loopback 例外。

9. **不建立服务端地址目录。** 所有旧地址同时永久失效时，本阶段不保证自动再发现；用户重新配对或修复宿主配置，界面显示各路径最后的失败原因。不引入 mDNS / Bonjour、服务端地址缓存、多手工 direct 地址或嵌入式 Tailscale。

## 考虑过的方案

- **先单地址配对、连上后再学习**：实现小，但首次配对仍然只有一条路；relay 不可用时，手机上根本没有机会学到直连。完整候选邀请的复杂度主要在解析和状态机，和半量方案差不多，所以不取。
- **服务端 endpoint directory**：能解决所有旧地址失效后的再发现，但无账号、扫码直连和服务端离线时仍需另一套机制；服务端要多存宿主网络地址；客户端的多路径与回退复杂度一点没少。因此选择宿主经配对和安全通道发布列表。
- **并行抢连接 / 延迟排名 / relay 可用时切 direct**：能更快选到低延迟路径，但要引入并发连接、取消和在线切换，且第一阶段只有一条活动连接。先用 relay 保证可用性，失败再 direct；以后由 #345 重新设计。
- **把 loopback 也写进宿主发布的远程集合**：会让远程客户端收到 127.0.0.1，既无用又误导。loopback 保持为客户端本机入口，由客户端自己保存。
- **所有错误都按关闭码判断**：裸 WebSocket close 没有经过 Noise 认证，不能当成宿主拒绝。错误分类同时看阶段、认证依据和作用域，身份变更仍需用户明确动作。

## 后果

- ADR-0015 后果中的“二维码里只有一个连接地址”由本 ADR 补全；ADR-0020 §4 的“配对链接选最远地址”改为“携带候选、Auto relay 优先”。ADR-0018 §4 的单地址关闭码规则只在候选内生效，整轮结束才汇总；ADR-0022 §4 的账号 Pair 响应 additive 转发候选，服务端不存 endpoint。
- 本阶段不改 WebRTC、TURN、多宿主同步、离线命令队列和 exactly-once；已发出但未收到响应的命令换路后不自动重放。
- Swift 钥匙串解码必须在每个宿主记录的可选 endpoint 边界容错：一个坏集合只失去该字段，不能让整份宿主列表解码失败，也不能损失设备密钥。
- 配对链接和 hello 的线上变化都按 ADR-0018 在同一主版本内新增次版本号；旧客户端忽略新增内容，旧宿主不发布该字段不会清空客户端已有集合。
