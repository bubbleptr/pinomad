# ADR-0018：协议兼容——主次版本号，同一主版本内只增不删，两端容忍不认识的内容

- 状态：Accepted
- 日期：2026-10-10

## 背景

ADR-0009 §8 让宿主在 hello 里带一个整数协议版本，客户端发现和自己的不相等就停下。这条规则只适合宿主自己提供的 Web 页面，那种情况下刷新一次就能对齐。ADR-0017 定了桌面端和移动端都把代码打包进 App，它们和宿主各走各的发布线，版本一定会错开。

几个现状：

- 版本号 4 天里从 1 涨到 4。v2（`answer`、`changes` 调用和两个展示类型）和 v3（`mcp` 流）都只是新增，v4 也基本是新增可选字段，唯一真正破坏旧客户端的是 `cycleThinking` 被换成了 `setThinkingLevel`。如果照严格相等的规则，每次新增都要所有打包客户端一起升级。
- 宿主遇到不认识的帧一律 `close(1008)`（`gateway.ts`），客户端遇到 4401 以外的关闭都会自动重连。版本检查一旦放宽，新客户端订阅旧宿主不认识的流时，就会陷入"被断开 → 重连 → 再被断开"的死循环。现在没出问题，只是因为 hello 阶段版本号就对不上，客户端提前停下了。
- snapshot 和 ops 里传的对话数据是 pi-durable 的类型（`ConversationView`、`EntryRecord`、`TaskGraph`），增量格式是 chord 的 delta。升级 `@earendil-works/*` 时这些结构可能变化，但协议版本号不会跟着动。

## 决策

1. **hello 里的 `protocol` 改成 `{ major, minor }`，同时带上宿主的版本号**（用于提示）。主版本号不同就拒绝连接；次版本号不同照样连接，客户端只在宿主的 `minor` 不低于某功能引入时的次版本号时才用这个功能。
2. **同一主版本内只允许新增**：可选字段、新调用、新流、新帧类型、新展示类型，每次新增次版本号加一。不删除、不改名、不改语义，可选字段不能改成必填。需要替换时（例如 `cycleThinking` → `setThinkingLevel`），旧的保留到下一个主版本再删。必须破坏时主版本号加一，次版本号归零。
3. **宿主遇到不认识的内容时回复错误，不断开连接。** 不认识的调用回 `result ok:false`，错误写"unsupported"；不认识的流回 `ended`，原因写"unsupported"；不认识的帧类型忽略。已知的调用如果参数格式错误、或者帧根本不是合法 JSON，就用关闭码 4400 断开，因为那说明客户端有 bug，不是版本问题。不用 1008：安全通道的握手超时、解密失败也用 1008，那些要能重连。
4. **客户端忽略不认识的帧类型和字段**；不认识的条目和展示类型走兜底渲染（ADR-0005）。收到 4400 关闭时和 4401 一样不再重连，因为重连只会得到同样的结果；1008 照旧重连。
5. **上游数据结构用契约快照盯着。** 从宿主录一组真实的 snapshot 和 ops 帧作为基准文件，测试里比对。升级 `@earendil-works/*` 本来就要显式评审（ADR-0002），评审时重新录制、看快照的变化：只是新增就把次版本号加一，有破坏就把主版本号加一。各个客户端（包括以后的 Expo）都用这组快照做解析测试。
6. **宿主只支持当前这一个主版本**，不为旧的主版本保留兼容代码。主版本升级时所有客户端一起升级；第 2 条的作用就是让这种情况很少发生。
7. **主版本不一致时的提示**：客户端比宿主旧，提示更新 App，并触发一次更新检查；宿主比客户端旧，提示在宿主上运行 `pinomad upgrade`。宿主提供的 Web 页面照旧自动刷新一次（ADR-0009 §8）。

## 考虑过的方案

- **维持严格相等，靠各端快速自动更新**（electron-updater、EAS Update）：规则最简单。但宿主和客户端是两条发布线，每次新增都要求所有端同时升级，任何一端更新慢了就连不上。
- **能力列表**（LSP、MCP 的做法）：hello 里列出支持的功能，按功能决定用不用。LSP 需要它，是因为几十个编辑器对几百个语言服务器，各自只实现了规范的一部分。我们只有一种宿主实现，客户端也都出自同一个仓库，版本历史是一条直线，一个次版本号就能说清楚；能力列表还只增不减，要测的组合也会变多。以后如果出现取决于宿主配置的功能（例如远端执行环境），或者某个客户端故意只实现一个子集、需要宿主知道，再给 hello 加一个可选的 `capabilities` 字段。这本身是一次新增，按第 2 条不用涨主版本，组合起来就和 MCP 一样：主版本管能不能连，能力管用哪些功能。
- **宿主把上游类型转换成我们自己的稳定数据结构（防腐层）**：客户端彻底不受 pi-durable 变化的影响，但要重写整个视图投影。等契约快照频繁报出破坏时再考虑。
- **宿主同时支持多个主版本**：旧客户端能多撑一段时间，代价是宿主里要一直留着兼容代码。这是一个人自托管用的产品，不值得。

## 后果

- 修订 ADR-0009 §8：版本比较从严格相等改为主版本相等，次版本号用来决定用哪些功能。
- 改变 hello 的结构本身就是破坏性变更，所以主版本号从 5 开始（现在的整数版本号是 4）。旧客户端拿 `{ major: 5, … }` 和 `4` 比较，结果是不相等，会照旧走"版本不匹配"，宿主提供的页面会自动刷新。
- `isClientFrame` 要能区分"不认识"和"格式错误"，现在两者都返回 false。
- 功能对应的次版本号要在 `packages/protocol` 里集中记录，客户端按它判断，不在各处散落数字比较。
- 我们自己的帧改了以后，加哪个版本号仍然靠人判断，契约快照只盯得住上游的数据结构。路线图"技术债"里那一条只解决了一部分。
