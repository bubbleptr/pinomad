# ADR-0043：宿主升级由宿主自己执行，客户端发起，可选闲时自动升级

- 状态：Accepted
- 日期：2026-11-06
- 修订 ADR-0009 §5（不排空）、§6（升级只有命令行）；ADR-0018 §7（主版本不一致时提示到宿主上运行命令）不变

## 背景

升级宿主只能在宿主机器的终端里跑 `pinomad upgrade`（ADR-0009 §6，打包安装由 ADR-0016 改成 `npm i -g pinomad@latest`）。客户端唯一提到升级的地方，是主版本对不上时提示"去宿主上运行 `pinomad upgrade`"（ADR-0018 §7）。可用户最常需要升级的时候，是人在外面、手里只有手机，最没法开终端。

几个现状：

- `upgrade` 是一个外部进程。它先用 token 连上宿主等任务结束（`waitUntilIdle`），再装新版本，最后交给服务管理器重启。从检查完空闲到宿主真正停下之间有一段竞态窗口，ADR-0009 §5 接受了它，没有给网关加"排空"状态，理由之一是各个客户端都得能把这个状态显示出来。
- 服务定义：launchd 是 `KeepAlive=true`，进程无论怎么退出都会被拉起（约 10 秒节流）；systemd 是 `Restart=on-failure`、`RestartSec=2`，只有非 0 退出才会拉起。
- `systemctl --user restart` 会杀掉整个 unit 的 cgroup。宿主自己调起的子进程也在这个 cgroup 里，所以宿主不能靠"调起 `pinomad upgrade` 让它来重启我"。launchd 的 `kickstart -k` 也会连带处理同一进程组。
- 打包安装是单个 JS bundle（ADR-0016），但启动之后还有懒加载的依赖：终端用的 `@lydell/node-pty`（ADR-0041）和 P2P 用的 `node-datachannel`（ADR-0033）。`npm i -g` 是原地替换文件的。装完以后宿主如果接着跑，后面再加载进来的就是新版本的模块，新旧代码会混在一起。
- hello 已经带着 `hostVersion`（ADR-0018 §1）。主版本不一致时，Web 客户端和 Rust 核心在 hello 之后立即断开、不进入 ready（`remote-durable.ts` 的 `#onHello`、`remote_durable.rs`），所以这时客户端读不到任何宿主流，也发不了调用。宿主不知道自己是不是由服务管理器托管，但能像 `upgrade` 那样调 `serviceManager().state()` 自己去查。
- npm registry 里每个版本的文档就是发布时的 `package.json`，另外还有每个版本的发布时间（`time`）。`apps/cli/build.ts` 生成的 `package.json` 现在不带协议版本号。

## 决策

1. **升级由宿主进程自己执行，客户端通过调用发起。** 宿主负责查新版本、等空闲、安装和退出；客户端只负责显示状态和发起调用。任何已配对的设备都能发起：这些设备本来就能让 agent 跑 bash，没有扩大权限。

2. **宿主怎么重启：装完新版本后自己退出，退出码固定为 75（`EX_TEMPFAIL`），由服务管理器拉起来。** launchd 本来就会拉起；systemd 的 `Restart=on-failure` 也会拉起非 0 退出，所以已经装好的服务定义不用重新 `install`。宿主不调起外部进程来重启自己。重启间隔取决于服务管理器（systemd 约 2 秒，launchd 最多约 10 秒），客户端在这段时间里按正常断线重连（ADR-0032）；宿主提供的 Web 页面照 ADR-0009 §8 自动刷新。

3. **顺序是：等空闲 → 排空 → 安装 → 退出。** 修订 ADR-0009 §5：
   - **等空闲**：没有未结束的任务，也没有等待中的 `approval.wait`。判断在宿主内部做，直接读任务图，不再从外面连进来轮询。
   - **排空**：空闲以后，宿主进入"升级中"，拒绝会启动 agent 工作的调用（`submit`、`createConversation`、`runCommand`、`compact`、`answer`），返回明确的错误，客户端据此显示"宿主正在升级"。这样就没有 ADR-0009 §5 接受的那段竞态窗口了。ADR-0009 当时不做排空，是因为各个客户端都要能显示这个状态；现在升级入口就在客户端上，这一条已经必须显示了。
   - **安装**：复用 `upgrade` 现有的安装步骤（`npm i -g --prefix <本包所在的前缀>`，npm 用运行宿主的那个 Node 旁边的那份，见 #499），只是改成在宿主进程里跑。装的是这一次通过检查的那个确切版本（`pinomad@<版本号>`），不是 `pinomad@latest`：从检查到安装之间可能要等空闲，这期间 `latest` 可能已经指向一个没检查过的版本，比如不满 3 天、或者跨了主版本。CLI 在本地路径上照旧装 `latest`。
   - **退出**：安装成功就立刻退出，不再加载任何东西，避免上面说的新旧模块混用。
   - **失败**：安装失败时，宿主退出"升级中"、恢复接收提交，继续跑已经加载的旧代码，并把错误（npm 输出的末尾几行）报给客户端。`npm i -g` 不保证原子性，装到一半失败可能留下一棵不完整的目录树，宿主下次启动时才会暴露。这个风险写在后果里。
   - **立即升级**：跳过等空闲，直接排空、安装、退出。正在跑的工作交给 Durable 恢复，和 `restart --force` 一样。

4. **只有"打包安装、服务已安装且在运行"时才能从客户端升级。** 其他情况宿主照样报告新版本，但不接受升级调用，客户端改成显示要在宿主上执行的命令：
   - 源码检出：这是开发路径，可能有未提交的改动，升级要 `git pull` 加重新构建，仍然走 `pinomad upgrade`。
   - 没装服务，或者被 `service stop` 停掉（#501）：宿主退出后没有东西会把它拉起来。

5. **宿主怎么知道有新版本：读 npm registry 里 `pinomad` 的文档，取 `dist-tags.latest`、这个版本的发布时间和协议主版本号。** 打包脚本在生成的 `package.json` 里加一个 `pinomad.protocolMajor` 字段。没有这个字段的版本（也就是所有已经发布的版本）一律当作跨主版本处理。启动时查一次，之后每 6 小时查一次，客户端也可以要求立刻查。请求走宿主进程的代理环境变量。`off` 档完全不查。

6. **闲时自动升级是宿主设置 `autoUpgrade`，取值 `off` / `notify` / `auto`，默认 `notify`。** 跟其他宿主设置一样存在数据目录的 `settings.json`、经 `settings` 流推送（ADR-0021）。
   - `notify`：只查、只提示，升级由用户在客户端上发起。
   - `auto`：满足下面全部条件时，宿主自己发起一次"闲时升级"：
     - 新版本和当前版本的协议主版本相同。跨主版本会让还没更新的 App 连不上（App Store 和 TestFlight 比 npm 慢），所以只能手动，客户端在确认时把这个影响写清楚。
     - 新版本发布满 3 天，给有问题的版本留出撤回的时间。
     - 宿主已经连续 15 分钟没有活动：没有未结束的任务，没有新提交，也没有任何终端有输出。终端（ADR-0041）在内存里，宿主一重启就没了，所以有终端在出输出就不算空闲；只是开着、没有输出的终端不挡升级。
     - 这个版本之前没有装失败过。装失败的版本，`auto` 不会再自动重试；用户可以在客户端上手动重试，或者等下一个版本。
   - 客户端发起的"闲时升级"只等第 3 条里的空闲，不受 15 分钟和 3 天的限制。会关掉终端时，在确认的时候提示。
   - "装失败过"的记录按版本号记。

7. **宿主通过一条宿主流推送升级状态，客户端通过调用操作，都是新增，涨次版本号（ADR-0018 §2）。**
   - 流里的内容：当前版本；可用的新版本（版本号、发布时间、是否跨主版本）；能不能从客户端升级（不能时附原因：源码检出 / 没装服务 / 服务已停）；当前阶段（空闲、正在查、等空闲、排空中、安装中、失败及错误）。
   - 调用：发起升级（闲时 / 立即）、取消（只在等空闲的阶段有效，开始安装后就不能取消了）、立刻查一次新版本。
   - `crates/pinomad-core` 同步实现，重新生成对照向量。

8. **升级入口只在两端主版本相同、连接正常的时候出现；主版本不一致时仍然按 ADR-0018 §7 显示命令。** 主版本不一致时连接在 hello 后就断开了（见背景），客户端拿不到升级状态，也发不了调用。为这一种情况再开一条跨主版本也不变的管理通道，代价太大（见考虑过的方案）。补救的办法是让跨主版本的升级尽量在旧连接还在的时候做完：只要宿主有新版本，客户端就一直显示，包括跨主版本的版本。所以 App 升级到新主版本之前，用户可以先用旧 App 把宿主升上去；这时提示的是"升级后，还没更新的 App 会连不上"，而不是反过来。

9. **`pinomad upgrade` 保留，但只有一份实现。** 打包安装且服务在运行时，CLI 连上宿主、发同一个调用，然后跟着流打印进度；源码检出、没装服务、服务装了但宿主连不上（比如新版本起不来）时，走现在的本地路径。CLI 和宿主共用同一个安装函数，安装逻辑不写两份。桌面端的宿主启动器（ADR-0017 补充）照旧只管安装、启动和停止；桌面端连着宿主，是一个普通客户端，升级入口和 Web 是同一个。

10. **仍然不做监管进程，也不做自动回滚。** ADR-0009 说过，中继要求升级时设备不断连、或者需要失败自动回滚时，再考虑监管进程。现在中继已经有了，但升级时断开十几秒、然后自动重连，对一个人自托管的宿主来说可以接受。新版本起不来时，用户要像今天一样在宿主上手动处理，比如 `npm i -g pinomad@<旧版本>`。第 6 条的 3 天冷静期和"只在同一主版本内自动升级"就是为了让这种情况尽量少发生。

## 考虑过的方案

- **客户端直接让宿主执行 `pinomad upgrade`**（比如用 agent 的 bash 或者一个"运行命令"调用）：改动最少，但在 systemd 上重启会杀掉升级进程自己，进度和失败原因传不回客户端，竞态窗口也还在。
- **宿主调起一个脱离 cgroup 的升级进程**（`systemd-run --user --scope`、launchd 上用 `setsid`）：外部进程的思路就能保留下来，但每个平台要单独适配。宿主"装完就退出"在两个平台上都直接成立。
- **改成 `Restart=always`**：语义更直白，但已经装好的服务都得重新 `install`。固定一个非 0 退出码，不用迁移。
- **装到新的前缀里，再切换服务定义指向**（蓝绿式）：装到一半失败也不会动到旧版本，还能回滚。但这要改服务定义，还要改分发布局（ADR-0016 的全局 npm 安装），改动太大。等装坏的情况真的出现了，再考虑。
- **一条跨主版本也不变的升级管理通道**（hello 之前或之外，单独定一套永不改的帧，只用来读升级状态、发起升级）：主版本不一致时也能从客户端升级，是唯一能覆盖"App 先更新了"这种情况的办法。但它要和安全通道、多候选（ADR-0032）、P2P（ADR-0033）一起永远保持兼容，这违背 ADR-0018 §6"宿主只支持当前主版本"。第 8 条的提前显示已经覆盖了大部分情况。
- **从 semver 推断是否跨主版本**：包的版本号（0.x）和协议主版本号是两套各自独立的数字，推断不出来。所以要在 `package.json` 里显式写出来。
- **`auto` 也允许跨主版本，旧客户端连不上时提示更新 App**：宿主这边省事了，但用户会在外面突然连不上自己的宿主，而 App 更新要等审核，用户自己没法马上解决。
- **加"只在某个时段（比如夜里）升级"的设置**：有了 15 分钟无活动的条件，夜里自然会满足，另加时段只是多一个配置项。真有需要再加。

## 后果

- 修订 ADR-0009 §5：从客户端或 CLI 发起的升级有"升级中"状态，宿主会拒绝新提交；`pinomad service restart` 不改，仍然是等空闲、有竞态窗口。
- 修订 ADR-0009 §6：打包安装加服务在运行时，升级由宿主执行，CLI 只是一个客户端。
- ADR-0018 §7 不变：主版本不一致时仍然只显示命令。App 先升级到新主版本、宿主还没升的话，用户还是得去宿主上操作。
- 打包脚本要往 `package.json` 写 `pinomad.protocolMajor`。第一个带这个字段的版本发布之前，`auto` 实际上不会触发。
- 宿主多了一个对外的网络请求（npm registry）。`off` 档完全不请求。
- `npm i -g` 装到一半失败可能留下不完整的安装，宿主下次启动才会暴露，自动回滚不在范围内。`auto` 会在没人看着的时候装，所以这个风险比手动升级大，3 天冷静期是唯一的缓解。
- 宿主停机期间（几秒到十几秒），所有客户端断线重连，正在打开的终端会被关闭。
