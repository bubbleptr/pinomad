# ADR-0010：Git 项目的对话默认在独立 worktree 里工作

- 状态：Accepted
- 日期：2026-10-07

## 背景

ADR-0007 规定第一版只有一种执行检出，就是项目目录本身，并把 worktree 和"fork 时检出怎么处理"留到以后。服务模式（ADR-0009）加远程访问（ADR-0008）之后，最自然的用法是在手机上对同一个项目同时开好几个任务。现在这些对话都在同一个目录里读写文件，互相改到对方的文件，一条对话跑的测试也会看到另一条对话改了一半的代码。

Durable 能提供的：每条对话的 agent 有自己的 `cwd`；创建和 fork 对话时都能在同一个提交里改 agent 设置、写文档；执行环境由宿主的 `env` 回调在每次使用时构建，可以异步。Durable 不知道文件状态，fork 只分叉上下文，不分叉文件，也没有记录"某条消息那一刻文件是什么样"。

## 决策

1. **Git 项目的新对话默认得到自己的 worktree。**
   - 宿主在项目所在仓库上 `git worktree add`，为这条对话新建一个分支，起点是项目目录当时的 HEAD。项目目录里未提交的改动不带过去。
   - 项目是仓库的子目录时，worktree 仍然是整个仓库，对话的 `cwd` 是 worktree 里对应的子目录。
   - 新建对话时可以选"直接在项目目录"，适合想让本机正在跑的开发服务器立刻看到改动的场景。
   - 非 Git 项目、还没有任何提交的仓库，照旧用项目目录。Chat 不变。

2. **worktree 放在数据目录下**（`<数据目录>/worktrees/<对话 id>`），不放进项目目录。这样不会污染用户的仓库，不需要改 `.gitignore`，删数据目录也能一并带走。分支名带 `pinomad/` 前缀，再加一段随机后缀，避免两个数据目录（比如开发用的临时目录）登记同一个仓库时撞名。

3. **改动怎么回到项目，第一期只留分支。** agent 可以在自己的 worktree 里 commit，也可以 push、开 PR；合并由用户自己做。宿主不在项目目录里执行 merge，也不碰项目目录的工作区。

4. **fork 得到一个新 worktree，内容是父对话检出在 fork 那一刻的状态。** 包括父对话已提交、未提交和未跟踪（未被忽略）的改动；被忽略的文件不带。之后父子两边互不影响。文件是 fork 那一刻的，不是 fork 点那条消息时的，因为 Durable 没有记录文件历史；界面上要说清楚。父对话在项目目录里工作时同样处理，Git 项目的 fork 总是得到新 worktree。Chat 和非 Git 项目的 fork 仍然共用父对话的目录。

5. **子代理和发起它的对话共用检出。** 子代理是这条任务的一部分，不是另起一个任务。

6. **检出记录存在 Durable 里**：ADR-0007 的索引文档记下每个 worktree 属于哪条对话、路径、分支和起点（fork 还有快照），和对话本身在同一个提交里写入（创建和 fork 都是）。依据仍然是 ADR-0002：Durable 存储是唯一事实来源；客户端订阅索引就能看到分支。磁盘上的 worktree 只在一个地方建：宿主构建执行环境时（`env` 回调）发现目录不在，就按记录建好，分支已存在时复用分支。第一次使用、宿主在提交后崩溃、用户手动删了 worktree、取消归档后再用，走的都是这一条路径。fork 的快照必须在提交前取，因为它记录的是父检出在 fork 那一刻的文件。

7. **归档时清理目录，不删分支。** 归档对话时，worktree 没有未提交的改动就删掉目录，有的话保留并提示用户。分支永远不自动删，因为它可能还没合并。取消归档后按第 6 条的方式重建。归档一条顶层对话时，挂在它下面的 fork 的 worktree 一起按这个规则清理。

8. **环境准备第一期交给 agent。** 新 worktree 没有 `node_modules`、`.env` 这类被忽略的文件。宿主不做额外的复制或 setup 脚本，只在系统提示词里告诉 agent：这是一个新检出，在哪个分支上，需要的话按 AGENTS.md 自己装依赖，不要去改项目目录。

9. **上下文按项目的位置读取。** worktree 在数据目录下，它往上的目录里没有项目原来的 AGENTS.md（比如 `~/code/AGENTS.md`）。对话在 worktree 里时，仓库根目录以上的 AGENTS.md 按项目目录的路径读取，仓库内部的按 worktree 读取，读到的结果和直接在项目目录里工作时一致。

## 考虑过的方案

- **默认项目目录，勾选才用 worktree**：改动最小，但并行时很容易忘了勾，等到两条对话互相改坏了才发现。
- **Git 项目总是 worktree**：最简单，但想让开发服务器立刻看到改动时没有办法。
- **宿主提供"合并到项目当前分支"的操作**：要处理冲突，还要处理项目目录本身有未提交改动的情况，而且等于宿主替用户在主工作区里执行 Git 操作。第一期先不做，等确实有需要时再加。
- **fork 共用父对话的检出**：最简单，但 fork 的典型用途是"换个思路再试一次"，和父对话同时跑会互相改文件，正是这次要解决的问题。
- **fork 只带父分支已提交的内容**：实现简单，但父对话的改动通常还没提交，fork 出来的对话看不到刚才讨论的代码，和上下文对不上。
- **worktree 放在项目目录里（如 `.pinomad/worktrees/`）**：编辑器和工具更容易找到，但要改用户的 `.gitignore`，而且很多工具会递归扫描到这些副本。
- **项目级 setup 脚本或复制被忽略的文件**：环境更可靠，但多了一个配置入口，要复制哪些文件也得另外定义。先观察 agent 自己装依赖够不够用。
- **不用 worktree，直接 `cp -r` 或用 APFS clone 复制目录**：能带上被忽略的文件，但不是 Git 项目也照样复制，大仓库成本高，改动也没有分支可以合并回去。

## 后果

- 每条项目对话都多一个分支和一份工作区副本。对象库是共享的，占的空间主要是工作区文件本身；装依赖会再多出一份 `node_modules`。
- 项目目录的 `.git/worktrees/` 里会登记这些 worktree。移动或删除数据目录后，用户需要在仓库里执行 `git worktree prune`。
- 同一个仓库上的 Git 操作（建 worktree、为 fork 做快照）要在宿主里按仓库串行执行，避免 `index.lock` 冲突。
- 第一期没有界面上的合并或 diff 审阅，用户要在自己的终端或编辑器里看分支。`pinomad.diff` 以 worktree 的起点为比较基准，见路线图。
- 本 ADR 之前创建的项目对话不迁移，继续在项目目录里工作。
- 协议要改：新建对话时可以选检出方式；客户端能看到对话的检出类型和分支。
