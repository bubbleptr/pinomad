# ADR-0019：fork 共用父对话的检出，只有一层，每条消息最多一个

- 状态：Accepted
- 日期：2026-10-10
- 修订：ADR-0010 §4

## 背景

ADR-0010 §4 规定，Git 项目的 fork 会得到一个新 worktree，内容是父对话检出在 fork 那一刻的快照。重新设计 fork 和子代理的界面时（路线图 M2.5），这条规定暴露出几个问题：

- 检出由程序替用户决定。很多 fork 只是换个问法，或者在同一份代码上接着讨论，用不着另一份文件。真需要隔离时，agent 自己就能用 git 开 worktree，然后用绝对路径在里面读写：read / write / edit 不把路径限制在 cwd 里（`NodeExecutionEnv` 的 `resolvePath` 直接接受绝对路径），bash 也可以每次调用前先 `cd`。
- 快照加新 worktree 让 fork 变重：每次都多一个分支、一份工作区，往往还要重新装一遍依赖。
- 新界面把 fork 定成父对话的 thread：从某条消息开出，在父对话旁边的面板里对话。thread 里再开 thread、同一条消息上开好几个 thread，都没有实际用处，只会让面板变成一棵树。

## 决策

1. **fork 不新建检出，和父对话共用执行检出。** Git 项目、非 Git 项目、Chat 一律如此。宿主不取快照、不建分支，fork 的 agent `cwd` 就是父对话的 `cwd`。要不要隔离，由 agent 根据任务自己决定（比如 `git worktree add` 之后用绝对路径工作），或者由用户在消息里提出要求。宿主不提供检出选项。
2. **只有一层。** 只能从顶层对话 fork。fork 出来的对话和子代理的对话都不能再 fork，宿主拒绝这类请求。
3. **每条消息最多一个 fork。** 同一个 `entryId` 上已经有 fork 时，宿主拒绝再建；客户端遇到这种情况，直接打开已有的那个 fork。
4. **本 ADR 之前创建的 fork 不迁移。** 它们在索引里有自己的检出记录，继续按 ADR-0010 §6、§7 在自己的 worktree 里工作，也按那里的规则清理。已经存在的多层 fork，界面上归到它的顶层祖先下面显示。

## 考虑过的方案

- **保留 ADR-0010 §4 的做法（新 worktree 加快照）**：隔离最彻底，但每次 fork 都要付出 worktree 的成本，而大部分 fork 用不上。
- **fork 时让用户选检出方式（共用、新 worktree、交给 agent）**：原型里做过。每次 fork 都多一个要想的选项，而且宿主里并没有"交给 agent"对应的能力，到头来还是 agent 自己用 git 去做。
- **宿主提供"切到独立 worktree"的工具**：这样 Changes 面板和归档清理都能认出 agent 开的 worktree。但目前没有证据表明 bash 加 git 不够用，等真出了问题再加。
- **不限制层数和数量**：Durable 本身允许。但界面上会变成一棵树，原型里不管放进侧栏还是标签栏，都太长。

## 后果

- fork 和父对话同时运行时，会在同一个目录里改文件。这和子代理现在的情况一样，只靠提示词约束。fork 的系统提示词要说明两点：检出和父对话共用；需要隔离就自己开 worktree，并全程使用绝对路径。
- 宿主不知道 agent 自己开的 worktree：Changes 面板只显示共用检出里的改动；归档时不会清理它们，分支和目录要用户自己处理。agent 只要漏写一次绝对路径，文件就会落回共用目录，而且不会报错。
- fork 里的文件不再是"fork 那一刻"的快照，所以 ADR-0010 §4 里"界面上要说清楚 fork 时文件是什么状态"这条要求不再需要。
- 协议要改：`fork` 多了两种失败原因（层数超了、消息上已有 fork）；客户端需要知道每个 fork 是从哪条消息开出的，对话摘要里要带上分叉点。按 ADR-0018，这些都属于新增，次版本号加一。
