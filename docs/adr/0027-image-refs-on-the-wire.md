# ADR-0027：图片在线上按内容引用传，存储不变

- 状态：Accepted
- 日期：2026-10-23
- 回答 ADR-0024 §5 里图片的那一半："每次交付整份还是只交付变化"中，图片随快照往返的部分

## 背景

消息和工具结果里的图片以 base64 内联在 pi-durable 的条目里（`entries.record` 的 JSON），对话视图原样带着它们。订阅对话时宿主先发一份完整视图，每次重连、每次重新打开对话都再发一遍，没看到的图也一起传；iOS 上每份快照还要带着图片过 Rust/Swift 桥。#157 的真机实测：一条带 4 张图的消息约 5.4MB base64，300 轮带图对话的流式快照 p95 已经接近 30ms 预算。

用户发的图在客户端压缩过（长边 1568px JPEG），工具结果的图（`read` 读图、MCP 截图）没有，单张可以到 4.5MB base64。

## 决策

1. **存储不动**：图片继续内联在 SQLite 的条目里。
2. **线上按内容引用传**：客户端订阅 `conversation:` 流时声明 `images: "ref"`，宿主发出的 snapshot 和 ops 里，`{type:"image", data, mimeType}` 换成 `{type:"image", mimeType, ref}`。`ref` 是 `sha256(mimeType + "\n" + data)` 的 hex——它同时绑定类型和字节，同一段字节按 PNG 和 JPEG 发送是不同的图。改写只发生在三个 content 数组的元素上，按路径判断，不按 JSON 形状递归：
   - `entries[i].model[j].content[k]`（pi-durable `EntryRecord.model: Message[]`，含 user / toolResult / assistant 消息）；
   - `docs["pi.inbox"].items[i].content[k]`（`InboxItem.content: UserInput`，可能是字符串）；
   - `docs["pi.live"].generation.message.content[k]`（进行中的 assistant partial）。

   工具 `details`、调用参数里恰好长成 `{type:"image", data, mimeType}` 的对象是数据，原样保留。
3. **按连接、按当前视图担保**：新调用 `image({ ref })` 只回答这条连接上仍然订阅着的 ref 流**当前视图**里的图片。宿主不累积 ref 表，也不另存一份字节；每个 ref 订阅只保留 `#forward` 里那份原始 `before`，收到请求时在这条连接所有 ref 订阅的当前视图里，按第 2 条的位置找 ref 相等的块。哈希仍用 WeakMap 按块对象缓存，所以查找不重复算哈希。ref 只要还在任一当前视图里就有效；撤回、删除或移出视图后失效。
4. **逐条 op 跟踪中间状态**：每批 ops 按顺序对原始状态逐条 `applyImmutable`，每条 op 用它**执行前**的状态判断是否触及图片块内部；只要有一条触及，就整批发 `["r", 改写后的批后视图]`。只看批前/批后两个端点会漏掉同一批里先插入、再原地修改、再移动的图片块（chord 1.2.0 上可复现 `unresolvable path`）。
5. **发送时可以回传 ref**：`submit` / `createConversation` 的图片可以是 `{ ref }`，宿主用自己记录的 mimeType 和字节换回，再做同样的 `imageProblem` 校验。ref 在 `#call` 的任何异步等待之前解析：提交帧到达时订阅还活着，客户端紧接着退订不能让已到达的提交失败。编辑排队中的消息要先 `image` 取回字节再撤回（撤回后该项离开 `pi.inbox`，ref 失效）；只有重试依赖回传 ref——失败运行的用户消息仍在对话视图里，ref 继续有效。同一设备发送时，客户端可以按同一规则本地算出 ref 预填缓存，不必等宿主发 snapshot。
6. **只增不删（ADR-0018）**：订阅参数是可选的，旧宿主忽略它、照旧内联，旧客户端不受影响；`image` 调用和回传 ref 记在 5.15。客户端两种形式都要认。

## 考虑过的方案

- **图片另存文件或单独的表，条目里只放引用**：模型每轮都要原始字节，得在上游组装上下文时把字节填回去，pi-durable 1.2.0 没有这个钩子；还会失去一个文件带来的原子提交、fork 共享和备份，要自己管引用计数和孤儿清理。真正贵的是反复传输，不是存储。
- **宿主持久化一张 `hash → 字节` 表**：宿主重启后旧 ref 照样能查，但同一张图存两份。客户端重连时会收到新的快照，宿主随之重新登记 ref，用不着持久化。
- **按位置编号（条目 id + 第几块）**：不用算哈希，但工具结果图先出现在 `pi.live`、之后才写进条目，位置一变就要重新下载；fork 和不同对话里的同一张图也没法共用缓存。
- **升主版本号，所有流一律传 ref**：宿主少一条路径，但手机上还没更新的 App 会直接连不上。
- **按 JSON 形状递归找图片块**：实现短，但会把工具 `details`、调用参数里的同名对象也换掉，客户端拿到的就不再是工具输出；按第 2 条的三个路径判断才有确定的语义。
- **只在批前/批后两个端点判断图片块**：少一遍逐条 apply，但同一批内的中间状态会让 op 落到客户端已经换成 ref 的位置上，chord 1.2.0 的插入—修改—删除序列能稳定复现。

## 后果

- 第一次看某张图仍然要传一次原图；首屏只有文字和 ref，图片随后补上。要让首次加载也变小，得另做缩略图。
- 宿主在订阅和每批 ops 时要遍历一遍图片块并算哈希（同一个块对象只算一次）。冷启动首次订阅要把整份视图里的图都算一遍：critic 用 300 轮 × 4.5MB 图测到约 559ms；本实现用 300 轮、100 张约 700KB base64 的对话实测 83–114ms（三次），按每 8MB 让出一次事件循环，期间最长事件循环停顿 6–11ms。
- 客户端在一段时间内要同时认内联字节和 ref 两种图片块。
- ref 只在有订阅的连接上有效：客户端想取某张图，得先订阅它所在的对话；编辑排队消息要先取字节再撤回。
