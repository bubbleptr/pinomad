# ADR-0042：Settings → Hosts 按机器呈现，"路"和"来源"分开

- 状态：Accepted
- 日期：2026-11-05
- 补充 ADR-0035 §4（三维状态在界面上的合成）和 ADR-0032 §2（候选在界面上的称呼）
- 讨论记录：[Settings → Hosts：按机器和到达路径呈现](https://claude.ai/artifact/1dXuQg37rSCwi7wGkKY1oZ)（私有 Doc）、[布局方向](https://claude.ai/artifact/6RJfbm9SH6iD11jHoHtnRk)（私有画布）

## 背景

#502 想把 Settings → Hosts 从"已配对宿主列表"改成"一台台机器，每台下面列出到达它的路"，并说"退出账号只少一条路"。这个说法来自 T3 Code 的路线模型（`docs/research/account-first-onboarding.md`），但和 PiNomad 的模型对不上：

- 中继是宿主发布的候选，扫码配对、粘贴链接和账号 Pair 拿到的是同一组候选（ADR-0032 §1）。账号不是一条路。
- 账号决定的是信任和登记：这台设备的密钥是不是服务端担保的（`StoredHost.account.vouched`），以及账号下的新机器会不会自动登记（ADR-0035 §5）。
- 截至 `bubbleptr/pinomad@c299d407`，普通退出登录不删任何宿主；勾上"公用电脑"才忘掉经账号担保的宿主，扫码配对得到的密钥保留。

现在的 Hosts 列表只在聚焦的那台或打开了 Connection 面板的那台上显示当前路径，账号在单独的对话框里，用户看不出一台机器有几条路、哪条不通、凭什么被接受。

## 决策

1. **每台机器分两层呈现。** 上层是"路"（ADR-0035 §4 的连接维度），下层是"怎么认识的"（信任维度）。退出账号在界面上只改变下层，路不变。
2. **来源从 `StoredHost` 推出，不新增存储。** `account.vouched` 为真显示"账号"；有 `account` 但没有 `vouched`，说明是关联到账号的扫码配对，显示"扫码配对"和"账号"两项；没有 `account` 显示"扫码配对"。
3. **直连在客户端按地址细分，只用于显示。** `100.64.0.0/10` 或 `.ts.net` 显示为 tailnet，私有网段显示为局域网，其他显示为"直连"。协议和 `EndpointSet` 不变，ADR-0032 §2 的"候选不写厂商名"仍然只约束线上格式。
4. **所有路都列出来。** 当前环境里注定不通的路（例如 ADR-0032 §6 说的 HTTPS 页面上的 `ws://` 直连）置灰，写明原因；失败过的写最近一次失败的原因。用户由此知道为什么只能走中继。
5. **Hosts 列表去掉 Switch。** Providers 等宿主级设置已经有自己的机器选择器（#427），切换聚焦靠侧栏的机器分组，列表里的 Switch 没有用处。

## 考虑过的方案

- **按来源分组**（"账号里的机器"和"扫码配对的机器"）：同一台机器可能两种来源都有，分组后要么出现两次，要么得硬选一组；用户先关心的是能不能连上。
- **只列路，把账号当成一条路**（#502 原文的字面读法）：退出账号后中继照样能用，界面却显示少了一条路，会误导。
- **在协议里给直连候选标网络类型**：要改 hello 和配对邀请的格式（ADR-0018 的次版本），只为一个显示用的标签，不值得；地址推断已经够用。

## 后果

- 布局方向待实现时再定。画布上推荐 A1 卡片（每台机器一张卡，路和来源都直接可见），机器多了会很长，届时可以再评估列表加详情。
- 地址推断会把同样用 CGNAT 段（`100.64.0.0/10`）的其他 VPN 误标成 tailnet。这只影响显示，不影响连接。
- Connection 面板（连接模式、P2P 状态）保留，它管的是怎么连，不属于本 ADR 的范围。
- iOS 的 Hosts 页按同一模型呈现，界面另行设计。
