# ADR-0007：项目 → 对话的工作组织模型

- 状态：Accepted
- 日期：2026-10-06

## 背景

骨架阶段一个宿主只有一条主对话，cwd 在启动时由 `--cwd` 固定。开新任务只能 fork 或 compact，换项目要换数据目录、重启宿主。ADR-0003 把"会话、代码项目、执行检出和 Durable 对话怎么对应"留作待决。

Durable 1.0 能提供的：一个 Session 存任意多条对话（保留的根对话、`createConversation` 新建的独立对话、从某条消息 fork 的对话、子代理任务拥有的对话），每条对话有自己的 agent 设置（cwd、模型、扩展）。它不提供项目概念，也不能删除对话。

## 决策

1. **主模型是"项目 → 对话"**，术语见 CONTEXT.md：项目、对话、Chat、执行检出。
   - 项目是手动登记的本地目录，以规范化后的绝对路径作为身份，同一路径不重复登记。移除项目不删目录，也不删历史对话。
   - 每个任务一条对话。不属于项目的对话是 Chat。
   - 从对话中 fork 出的对话和子代理的对话挂在发起它的对话下，界面上以 thread 呈现，不进入顶层列表。
2. **不采用 channel / thread 作为主模型**：没有长期存在的项目主对话。thread 的体验由 fork 和子代理提供（Durable 的 fork 本来就是"从某条消息开出、继承到那里为止的上下文"）。
3. **执行检出**：第一版只有一种，即项目目录本身；Chat 的执行检出是 `<数据目录>/chats/<对话 id>`，在创建对话时由宿主建好。对话的 agent `cwd` 就是它的执行检出。Git worktree 作为第二种执行检出以后再做，fork 时检出怎么处理也到那时一起定。
4. **存储**：项目登记表和顶层对话的索引（归属的项目或 Chat、标题、是否归档）存在 Durable 的 session 级文档里，不另外存配置文件。新建对话时，对话本身和它的索引项在同一个提交里写入；客户端以"快照 + 增量"订阅这份文档。理由：ADR-0002 规定 Durable 存储是唯一事实来源，而且这样能保证原子性，同步也不用额外实现。
5. **归档代替删除**：Durable 不能删除对话，所以"删除"做成归档标记，归档的对话不出现在默认列表里。
6. **不再使用根对话**：宿主不再调用 `harness.root()`，新对话的初始模型和思考等级取宿主的默认设置。骨架阶段的数据目录不迁移。
7. **宿主不再有固定的 cwd**：去掉 `--cwd`，改为可重复的 `--project <路径>`，在启动时登记项目，已存在的路径直接跳过。项目主要通过客户端登记：客户端提交路径，由宿主校验目录存在。

## 考虑过的方案

- **channel / thread**：channel 主对话要么在里面写代码，上下文越积越多；要么不写代码，变成空壳入口。channel 的长处（多人协作、@、异步通知）在自用的自托管工具里用不上，而且它解决不了同一目录下并行改文件的冲突。
- **每个项目一个 Durable Session（各用一个 sqlite）**：隔离更好，但一个进程要管多个 Harness 和调度器，跨项目列表要打开所有存储，网关也会更复杂。Durable 本来就是为一个 Session 承载很多对话设计的。
- **项目登记表存在单独的配置文件**：多了一个事实来源，新建对话和写索引无法放进同一个事务，客户端同步还要另做一套。

## 后果

- 协议要改：hello 不再给出 root；新增登记 / 移除项目、新建对话、归档；对话列表改为订阅索引文档。
- 骨架阶段的 `~/.pinomad` 数据目录（里面只有根对话）不会出现在新列表里，需要清掉重来。
- 对话标题暂时沿用第一条用户消息，自动起名以后再做。
- 同一项目下的并行对话在第一版会互相改到对方的文件，要等 worktree 才能解决。
