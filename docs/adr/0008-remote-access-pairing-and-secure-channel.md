# ADR-0008：远程访问——扫码配对、协议层端到端加密，中继分期

- 状态：Accepted
- 日期：2026-10-06

## 背景

ADR-0003 留下了"远程访问时客户端怎么认证、连接怎么加密、权限怎么控制"。现状：网关只监听 `127.0.0.1`，客户端用数据目录里一个长期有效的全局 token 认证，连接是明文 WebSocket；Web 客户端由 Vite 在本机 5199 端口提供。

agent 能在宿主上执行任意命令，所以能连上宿主就等于拿到了宿主的 shell。约束：

- 不能要求用户装特定的网络软件。Tailscale、ZeroTier、WireGuard 都要建虚拟网卡，常和用户已有的 VPN 冲突；有些代理软件（如 sing-box）能把 tailnet 当作入站节点，有些（如 Surge）只做出站，不能作为前提。
- 不能要求用户接受第三方看到对话和代码。Cloudflare Tunnel、ngrok 在它们那里终止 TLS，能看到明文。
- 最终要在任何网络下都能用，即宿主和手机都只主动往外连，经服务器中继。

## 决策

1. **加密做在 PiNomad 协议层，与传输无关。** 宿主和每台客户端之间建立端到端加密的**安全通道**，网关现有的帧全部在通道内传输。下面走局域网直连、用户自己的 Tunnel 或 tailnet、以后的中继，传的都是同一种密文。中继和 Tunnel 只看到密文。

2. **身份是密钥对。** 宿主有一对长期的 X25519 密钥，私钥存在数据目录（权限 0600，和现在的 token 一样）。每台客户端设备生成自己的密钥对，私钥不离开设备。

3. **扫码配对。**
   - 宿主按需显示配对二维码（宿主终端，或已配对的本机客户端里），内容是：候选连接地址、宿主公钥、一次性配对密钥（随机 128 位，几分钟内有效，用一次即作废）。
   - 设备扫码后和宿主握手，用配对密钥证明自己看到了二维码，同时把自己的公钥交给宿主。宿主登记这台设备（公钥、名字、配对时间）。
   - 二维码里不放长期凭证。截图泄露的后果只限于有效期内的一次配对。
   - 二维码用 `uqr` 生成（零依赖、ESM，能输出终端字符和 SVG）。

4. **握手用 Noise 协议框架的 IK 模式，配对时把一次性配对密钥放在握手第一条消息的加密载荷里**（只有宿主私钥能解开），宿主校验后作废。设备事先知道宿主公钥（来自二维码），握手第一条消息就带上自己的公钥；宿主只接受已登记且未吊销的设备。每次连接重新握手，得到新的会话密钥。

5. **密码学原语用 `@noble/curves`、`@noble/ciphers`、`@noble/hashes`**：X25519、ChaCha20-Poly1305、BLAKE2s 或 SHA-256。
   - 理由：纯 JS，宿主（Node）、浏览器、React Native（Hermes）三端都能用，Hermes 只需补 `getRandomValues`；2024 年经过 Cure53 审计；持续维护。
   - Noise 的握手状态机在 `packages/protocol` 里按规范自己实现，用公开的 Noise 测试向量校验。原语不自己写，协议不自己发明。
   - 不用 AES-GCM：noble 的 AES 只是 WebCrypto 的包装，React Native 没有 `crypto.subtle`。

6. **设备登记表存在 Durable 的 session 级文档里**（和 ADR-0007 的索引一样）。吊销设备时，宿主关闭这台设备当前的连接。任何已配对的客户端都可以列出和吊销设备。

7. **认证边界**：只监听回环地址时，沿用现在的 token（本机开发、本机客户端）。监听非回环地址时，只接受安全通道，不接受 token。默认仍只监听回环地址，开放局域网要显式加参数。

8. **权限**：第一版已配对的设备和本机客户端权限相同，没有只读设备，也没有按设备区分的审批策略。

9. **分期**：
   1. 安全通道、扫码配对、设备登记与吊销，传输只有局域网直连。宿主同时提供构建好的 Web 客户端，手机浏览器扫码即可打开。出门在外，用户可以自己用 Tunnel 或 tailnet 把宿主地址暴露出去，二维码里的候选地址可以手动指定。
   2. 可以自己部署的中继：宿主和客户端都主动连中继，中继按宿主身份（宿主公钥的哈希，宿主连接时签名证明）把两端的连接接起来，只转发密文，不存储。
   3. 官方中继、推送通知等，另行决定。

## 考虑过的方案

- **Tailscale 等虚拟网络作为前提**：最简单，加密和穿透都现成，但要建虚拟网卡，和用户已有的 VPN 冲突，不能要求所有用户安装。用户自己有的话，仍可以作为一种传输来用。
- **Cloudflare Tunnel / ngrok 作为方案**：不用写加密，但第三方能看到明文，入口暴露在公网，快速隧道每次重启地址都会变。只作为用户自选的传输。
- **局域网用 TLS 加自签名证书**：浏览器会弹证书警告，只解决局域网，中继还得另做一层加密。协议层加密一次解决所有传输。
- **`libsodium-wrappers`**：WebAssembly 版本在 Hermes 上用不了，React Native 要换成 `react-native-libsodium`，它只实现了部分 API，三端会用两套库。
- **现成的 Noise 库**：`noise-protocol` 依赖 libsodium 的原生绑定，2023 年后没有更新；`@chainsafe/libp2p-noise` 绑定 libp2p 的接口，只支持 XX；`salty-crypto` 还是候选版，原语是自己移植的，没有审计。
- **自己设计握手**：容易出错，Noise 已经覆盖了需要的性质（双向认证、前向保密、身份隐藏）。

## 后果

- **浏览器客户端的信任问题**：端到端加密的前提是客户端代码可信。第一期手机浏览器从局域网用 HTTP 加载 Web 客户端，同一局域网里的主动攻击者可以替换页面代码。被动窃听防住了，主动篡改页面防不住。完整的保证需要原生 App，或者从可信的 HTTPS 地址加载客户端。这会影响移动端的形态选择（PWA 还是 Expo），到时再定。
- 浏览器里设备私钥只能存在 IndexedDB 一类的存储里，能拿到页面执行权限的代码都能读到。原生 App 可以放进系统钥匙串。
- 中继能看到元数据：哪个宿主、哪台设备、什么时候连、流量多大。
- 协议要改：握手和加密帧在现有的帧下面多一层；客户端需要配对流程和设备管理界面。
- 要自己维护 Noise 握手的实现，用测试向量和握手失败的测试（错误的 PSK、已吊销的设备、篡改的消息）兜底。
- 宿主的生命周期（常驻、崩溃拉起、升级）是远程使用的前提，另见 ADR-0009。
