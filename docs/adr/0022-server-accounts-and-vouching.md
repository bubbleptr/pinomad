# ADR-0022：服务端上的账号——宿主、客户端、服务端三个部分，服务端为新设备担保

- 状态：Accepted（§2 的「现在不开放注册」已由 #449 的邀请码注册取代；§4 的账号 Pair 响应由 ADR-0032 补充 additive 转发候选；§6 的账号设备加入广播由 ADR-0035 修订，§8 由 ADR-0035 补充）
- 日期：2026-10-13

## 背景

ADR-0008 只有一种加设备的方式：在宿主终端或已配对的客户端上生成一次性邀请，5 分钟内扫码或把链接搬到新设备上。实际用下来有三个问题：

- 借来的电脑、重装的 App、清掉数据的浏览器，都得先找到一台已配对设备，或者 SSH 回宿主。
- 宿主不止一台（至少 Mac 和 Linux），每台都要分别配对。
- 中继靠 `relay-id` 加 `--allow-host` 手动登记宿主（ADR-0015 §3）。

讨论过程中依次考虑过：已有设备批准、宿主口令走 PAKE、宿主本地账号（Home Assistant 式）、控制面放在第一台宿主上（Portainer、Coolify 式）、用 tailnet 身份免配对（Tailscale `whois`）。参照的产品里，"登录账号就能用"的都有一个先存在的中心：VS Code Tunnels、Lody、ds-harness-remote、Agents Anywhere。其中 ds-harness-remote 和我们最接近：同样是 Noise IK 加 `@noble/*`，账号在服务端，服务端替新设备担保，业务流量端到端加密。

约束：现阶段只给自己用，但希望以后能开放给别人（托管实例加自部署）；可以接受信任自己部署的 VPS；扫码、局域网和 tailnet 直连要继续能用。手机上 Surge、sing-box 都能内置 tailnet 客户端，ADR-0008 背景里"有些代理软件只做出站"已经不再是障碍，但 tailnet 仍然不能作为前提。

## 决策

1. **三个部分：宿主、客户端、服务端。** 服务端是宿主和客户端都主动连接的中心服务：管理账号和账号下的宿主，为新设备向宿主担保，转发安全通道的密文，并提供 Web 客户端。它不执行任务，也不能解密安全通道。服务端由 `apps/relay` 演进而来，ADR-0015 的按连接拼接（§1）、Ed25519 登记签名（§2）、HTTPS 提供 Web 客户端（§4）、46xx 关闭码（§5）都保留；"中继"不再作为独立的部分，只是服务端的转发功能。

2. **账号在服务端。架构支持多账号，但现在不开放注册。** 服务端第一次启动、还没有用户时，用环境变量 `PINOMAD_SERVER_USER` 和 `PINOMAD_SERVER_PASSWORD` 创建唯一的用户（密码至少 12 位，存 scrypt 哈希），以后改密码用服务端的 CLI。官方实例和自部署版是同一份代码；官方实例由作者托管，现在里面只有作者一个人。服务端因此要有数据目录，存用户、账号绑定的宿主和登录会话，取代 ADR-0015 §3 的"中继不持久化任何东西"。

3. **宿主用一条命令加入账号。** 在已登录的 Web 或 App 里点"添加宿主"，得到一条带一次性令牌的命令（形如 `npm i -g pinomad && pinomad join <服务端地址> <令牌>`；令牌只能用一次，十分钟左右过期）。在要加入的机器上运行，完成安装服务、加入账号、连上服务端。已经装好的宿主也用 `pinomad join` 加入。账号绑定取代 `--allow-host` 白名单；Ed25519 登记密钥保留，用来证明对 `hostId` 的使用权。一台宿主最多加入一个服务端的一个账号：再跑一次 `join` 就换过去，`pinomad leave` 退出。

4. **服务端为新设备担保的方式：向宿主要一份普通邀请。** 客户端登录账号后看到账号下的宿主。第一次进某台宿主时，服务端经宿主的控制连接（`/host`）请宿主签发一份一次性邀请（就是现有的 `createPairing`），再交给这台设备；设备照 ADR-0008 的 IK 配对流程连上去。宿主公钥由服务端给出。宿主只多两件事：接受来自控制连接的"要邀请"请求，把这样登记的设备标成"账号"来源。用户感知到的只是第一次进某台宿主时多等一两秒。
   - 由 ADR-0032 补充：邀请和 `POST /api/hosts/:hostId/pairing` 的响应可以 additive 携带候选列表；服务端只转发，不持久化 endpoint。

5. **信任模型：服务端是新设备的信任根。** 被攻破的服务端（或者能碰到 VPS 磁盘和内存的厂商）可以给自己登记一台设备，从而拿到宿主的 shell；也可以在新设备第一次登录时给出假的宿主公钥，读到这台设备的流量。Noise 安全通道保留，它防的是被动泄露（服务端日志、反向代理、VPS 快照里不会有明文），已经登记的设备也不会被换掉宿主公钥。ADR-0008 §1 的"中继只看到密文"相应改成：服务端转发的只有密文，但它能为新设备担保。

6. **宿主仍然是最终裁决的一方。**
   - 设备登记表和吊销照旧按宿主分别管，存在每台宿主的 Durable 里（ADR-0008 §6）。在服务端退出登录，只是服务端不再替这台设备担保，不会吊销已经登记的记录。
   - 宿主默认接受服务端担保的设备，不需要另一台设备批准；登记时在所有在线的已配对设备上提示"新设备 X 通过账号加入"，设备列表标出每台设备的来源（账号 / 扫码 / 本机）。
   - 宿主设置里有"接受账号担保的设备"开关，默认开，关掉后只能扫码。
   - 服务端被攻破时，攻击者能新加设备，但撤销不了用户在宿主上做的吊销。

7. **其余加设备、连宿主的方式不变。**
   - 扫码配对照旧：宿主终端的 `pinomad pair`、Web 和桌面端的 Devices 对话框，移动端补上出示二维码。不做"新设备出示、老设备扫"。
   - 不单独做"恢复"：身份丢了的设备重新登录就是一台新设备，旧记录去宿主上吊销。设备全丢了也一样。
   - 宿主认的是设备公钥，不管设备怎么登记的，都可以经服务端连，也可以经局域网或 tailnet 直连。服务端不可用时，直连照样能用。tailnet 只是传输，不承担身份。

8. **多宿主由客户端汇总，宿主之间不同步。** 客户端列出账号下的所有宿主；每个对话只属于一台宿主，开始对话时选在哪台宿主上跑。配对信息、对话和设置都不在宿主之间同步。

## 考虑过的方案

- **已有设备批准新设备**：信任只落在设备密钥上，但新设备仍要先经中继找到宿主、等另一台设备在线批准；多宿主时每台都要批一次。
- **宿主口令走 PAKE（OPAQUE）**：服务端作恶也加不了设备，信任模型最好。但没有三端可用、审计过的现成库，要自己按 RFC 实现；每台宿主一个口令，多宿主要记好几个。
- **宿主本地账号**：顺序上最自然（先装宿主再建账号），没有中心也能用；但每台宿主分别登录、分别改密码，解决不了多宿主。
- **控制面放在第一台宿主上**：自部署时省一个服务，但那台宿主必须常开、能被别的机器连到；以后托管时还得把控制面拆出来。
- **tailnet 身份免配对**：宿主用 Tailscale LocalAPI 的 `whois` 认出同一个 Tailscale 账号的设备，零步骤、天然多宿主。但要求所有设备都在 tailnet 里，信任根变成 Tailscale 和登录它的 IdP；不在 tailnet 里的设备仍然要另一套办法。保留为直连传输。
- **GitHub OAuth 登录**：不存密码，也方便以后开放注册；但自部署的人要先去 GitHub 建 OAuth App。等开放注册时再加。
- **宿主用设备码加入账号**：适合没有屏幕的机器，但"复制一条命令到目标机器上跑"同时完成安装和加入，步骤更少。
- **服务端签票据、宿主验签**：不用经控制连接要邀请，但要多一把服务端签名密钥，宿主还得事先记住它。宿主本来就经 TLS 连向自己配置的服务端，控制连接已经能证明对面是谁。

## 后果

- ADR-0003 的"宿主 + 客户端"变成三个部分；ADR-0008 §1 的信任表述、§3 的配对来源被修订，§9 第三期的"官方中继"由本 ADR 决定方向；ADR-0015 §3（白名单、不持久化）被取代。
- `GLOSSARY.md`：新增"服务端""账号"，撤掉"中继"；"设备""配对""安全通道"相应修改。
- 服务端要持久化，数据目录和宿主一样只能有一个进程使用。部署在容器平台上要挂持久卷。
- 服务端能看到的元数据比中继多：账号、账号下有哪些宿主、每台设备何时通过账号加入。业务内容仍然看不到。
- 服务端不可用时，只剩直连和扫码；托管实例的可用性成了体验的一部分。
- 所有设备权限仍然相同（ADR-0008 §8），能进宿主就等于拿到宿主的 shell。所以"多个人共用一台宿主"、团队权限不在这个模型里，开放注册时每个账号只能看到自己的宿主。
- 以后要做的：`apps/relay` 改名为 `apps/server`、`--relay` 等参数随之调整；开放注册、OAuth、配额和限流；账号层面一键把某台设备从所有宿主上踢掉；设备记住宿主的多个地址并自动选择；客户端同时连多台宿主。都记在路线图。
