# ADR-0052：Inbox 的记忆、发件箱和 agent 环境之外的凭据

- 状态：Accepted
- 日期：2026-11-15
- 补充：ADR-0051 §5（记忆和固定上下文）、§9（`notify` 经发件箱投递）
- 修订：ADR-0049 §8（插件 API 加 `secrets`）

## 背景

ADR-0051 定下了 Inbox、worker、计时器、auto mode 和 `notify`。对照 Anthropic 的 [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents) 逐项核对后，还有三块没有着落：

- 记忆：文章列出四类记忆，分别是用户指令、关于用户的笔记、已经告诉过用户的事、每项任务的进度，另外还有一轮定期整理（文章叫 dreaming）。ADR-0051 只写了"每个新对话开始时加载处理规则"，后果一节把笔记和整理留到以后。每项任务都从新对话开始，比长对话更依赖记忆，留到以后不行。
- 发件箱：文章说只有一个 send 工具也够用，但要控制发送节奏、要能从投递失败里恢复，就需要发件箱表加一个投递器；还要用评测调消息量，宁可先少发。
- 凭据：文章推荐把凭据放在 agent 环境之外，由代理在请求发出时加上，agent 自己发的请求不带凭据。PiNomad 的 agent 和宿主是同一个系统用户，shell 能读到 `~/.config/gh`、`~/.ssh` 和环境变量里的 token；Inbox 的运行无人看管、读的又是外部内容，一次提示注入就能把 token 带走。

## 决策

1. **记忆按项目存在宿主的数据目录里，不进仓库。** 位置是 `<dataDir>/inbox/<项目>/memory/`，跟着宿主走，比任何一次运行都活得久。只存查不到的东西：issue、PR、提交已经在别处的，只存指针。分四类：
   - `instructions.md`：这个 Inbox 的处理规则，用户在 Tasks 页写（ADR-0051 §11），每次运行都加载。agent 只能读，不能改。
   - `notes/` 加 `notes/INDEX.md`：agent 学到的关于用户和项目的东西，比如偏好、纠正过的做法。每次运行只加载索引，需要时再读具体文件。
   - `tasks/<任务 id>.md` 加 `tasks/INDEX.md`：每项任务做了什么、还剩什么。任务的对话重新打开或压缩后，靠它接着做。每次运行加载索引和本任务的文件。
   - 已发消息：宿主从发件箱（第 4 条）取最近的若干条放进上下文，免得重复告诉用户同一件事。不由 agent 维护。

   agent 用一组记忆工具读写，只能碰这个目录。

2. **固定上下文保持精简、前缀稳定。** 每次运行的顺序固定：系统提示和工具，然后是处理规则、笔记索引、任务索引，最后才是事件。规则和索引不变时，前缀逐字节相同，能命中 prompt cache（pi-ai 默认开启 `cacheRetention`）；有测试校验同一项目连续两次运行的前缀一致。自动压缩之前，先提醒 agent 把进度写进任务文件：压缩会丢细节，该留的要先存下来。

3. **定期整理也是一个 Inbox 事件。** 每个 Inbox 一个定时事件，默认每天一次：开一次只有记忆工具的运行，合并重复、删掉过时的条目、写下只有跨任务才看得出的规律。它和别的任务一样排队，不另开 worker。

4. **`notify` 写进发件箱，由宿主的投递器发出。** 发件箱是会话级的 `pinomad.outbox` 文档，每条消息记来源任务、正文和投递状态。投递器负责：失败重试并退避、每小时的条数上限、免打扰时段、短时间内的多条合并成一条摘要。提问（"Waiting for your answer"）不经发件箱，照旧直接推，文章也允许延后调用的请求直接出现在界面上。

5. **默认少发，用评测调。** 默认的处理规则让 agent 只在用户需要知道或需要决定时才 `notify`，其余安静结束。评测是一组录好的事件夹具，用真实模型跑，对"通知 / 安静结束 / 提问"三种结局打分，用来调默认规则。它要调用真实模型，不进 CI。

6. **凭据只在 agent 环境之外。** 凭据存在宿主的凭据库里（数据目录下只有宿主进程能读的文件，或者系统钥匙串），只有宿主和插件的服务端能读到。agent 要用外部服务时，调插件注册的工具，比如 `github_comment`、`github_open_pr`、`git_push`；由插件在宿主进程里加上凭据再发请求。这是文章里代理的工具级版本：按工具划分，不按域名划分。插件 API 加 `secrets`（修订 ADR-0049 §8），用户在 Tasks 页填。
   - 后续（5.37）：凭据库是数据目录下的 `secrets.json`（权限 600，按插件和名字存）。宿主同时跑在 Linux 和 macOS 上，钥匙串也挡不住同一个用户的 agent，挡它是第 7 条沙箱的事，所以没用钥匙串；沙箱要把这个文件也列进禁读。插件用 `secret(name, { description })` 声明，在工具里用 `ctx.secret` 读；插件工具返回或抛出的内容里，这个插件已填的凭据由宿主换成 `[redacted]`。客户端用 `setPluginSecret` 填值或清空，`hello.plugins[].secrets` 和 `plugins` 帧只说填没填，读不回值。

7. **Inbox 的运行进沙箱，读不到用户的凭据。** 只靠第 6 条不够：shell 是同一个用户，照样能读 `~/.ssh`。所以 Inbox 运行里的 bash 等进程用独立的 HOME，去掉凭据类环境变量（`GH_TOKEN`、`*_API_KEY` 等），并由系统沙箱禁止读用户的凭据目录和钥匙串：macOS 用 Seatbelt，Linux 用 bubblewrap，具体规则在实现时定。沙箱是 auto mode（ADR-0051 §7）之外的第二道防线：分类器判断这次调用该不该做，沙箱保证就算判错，也拿不到凭据。编码模式不变。

## 后果

- ADR-0051 后果里的"笔记和整理留到之后"作废，由第 1、3 条接上。
- 外部事件源（ADR-0051 §10）上线前，除了 auto mode，还要有第 6、7 条：拿不到凭据的运行，读外部内容才算安全。
- 在 Inbox 里开 PR、推分支必须走插件工具，agent 自己跑 `gh` 或 `git push` 会因为没有凭据而失败。GitHub 插件要先于 GitHub 事件源完成，两者本来就是同一个插件。
- 沙箱是平台相关的代码。在没有沙箱实现的平台上，Inbox 不能接外部事件源。
- 记忆目录在宿主上，换机器不跟着走；备份和迁移宿主数据目录时一起带上。

## 没选的方案

- **出站 HTTPS 代理注入凭据**：最接近文章的原样做法，但要自签 CA 证书去截 HTTPS，还要让 agent 用到的每个工具都信任这张证书，侵入大；git over SSH 也接不进去。
- **把凭据放进环境变量**：只是不写进代码，agent 用 `env` 就能读到，挡不住提示注入。
- **记忆放在项目仓库里**（如 `.pinomad/memory/`）：会进提交、被别人看到，笔记里还可能有关于用户本人的东西。
- **记忆整理放进每次运行的结尾**：每次都多花一轮，又看不到跨任务的规律。
