# 以账号为主线的上手流程（设计草案）

Created: 2026-11-01
Status: draft

## 结论先行

- 把"官方服务端 + 账号"定为唯一的主路径。用户只需要理解两件事：**设备登录账号**，**宿主加入账号**。扫码配对、`--remote-port`、`pinomad link`、自部署中继都退到"不用账号"的高级文档里，功能不删。
- 宿主加入账号改成浏览器确认：`pinomad join` 不再需要先去网页复制令牌，终端给出一个短码，用户在已登录的官网上输入并确认。确认后服务端签发的仍是今天的 join token，`join.ts` 后半段不变。
- 参照 T3 Code：宿主这边收成一条 `pinomad up`（问清楚其他设备怎么连、加入账号、装服务），配一个自带 Node 运行时的安装脚本，"一行命令"才真正成立。
- 客户端只做控制面：Web、Mac App、iPhone 都不带 Node、不托管宿主进程。本机也跑宿主的 Mac 用户，和其他机器一样跑一次安装命令；Mac App 负责把命令递到终端里，之后用一个开关启停这台 Mac 上的宿主服务。
- 退出登录时可以选择"让这台设备离开所有宿主"，让"退出就看不到"在需要时成立。

## 现状

四种使用方式并列写在文档里，用户一开始就要选：

| | 宿主怎么启动 | 设备怎么接入 | 离家可用 | 推送 |
|---|---|---|---|---|
| A 本机 | `pinomad host` | 浏览器用 `pinomad link` 的 token 链接；Mac App 粘贴回环配对链接 | 否 | 否 |
| B 局域网 / tailnet | `pinomad host --remote-port 7422`（`service install` 再写一遍参数） | 每台设备对每台宿主各扫一次 `pinomad pair` | 只有 tailnet | 否 |
| C 官方服务端 | 网页 Add a host → 复制带令牌的命令 → `npm i -g pinomad && pinomad join …` | 登录后自动配对账号下的宿主 | 是 | 是 |
| D 自部署服务端 | 同 C，服务端换成自己的 | 同 C | 是 | 是（要自配 APNs） |

用户的困惑集中在：三种凭据（token 链接、设备配对、账号会话）并存；Web 从宿主端口打开没有账号入口、从服务端打开才有；扫码设备不在账号的设备列表里；退出登录后照样能用；iPhone 不能注册，推送却要账号。

文档也已经漂移：`official-server` 中英两份的第 3、4 步和 `usage.zh.md` 的 iOS 部分写着登录后要点 Pair，实际上 Web、Mac、iPhone 登录后都会自动配对（`autoRegister`，M8）。

## 目标旅程

### 新用户，宿主就在自己的 Mac 上

1. 在 pinomad.si 注册（邀请码），下载 Mac App。
2. App 里登录。没有宿主时，首页就是"添加第一台宿主"：一行安装命令和**在终端中运行**。
3. 点它，"终端"打开并开始执行：安装脚本装好宿主，`pinomad up` 打印短码。
4. 回到 App 输入短码确认。宿主加入账号、装成服务，App 自动配对，进入 Providers 接入模型。

### 新用户，宿主是另一台机器（Linux 服务器、Mac mini）

1. 在 pinomad.si 注册并登录。没有宿主时，主界面是"添加第一台宿主"，给出一行命令。
2. 在宿主机器上运行：

   ```sh
   curl -fsSL https://pinomad.si/install.sh | sh && pinomad up
   ```

   安装脚本自带 Node 运行时（见"参考：T3 Code"）；`pinomad up` 先问其他设备怎么连这台机器，默认"经官方服务端"。
3. 终端打印确认网址和短码（如 `WDJB-MJHT`），有桌面环境时自动打开浏览器。
4. 在已登录的官网上输入短码，看到这台机器的名字、系统、来源 IP 和指纹，点确认。
5. 终端显示加入成功，宿主装成服务；网页上宿主出现并自动配对。

### 再加一台设备

登录即可，账号下在线的宿主自动配对（不变）。

### 再加一台宿主

在那台机器上运行同一行命令，到任意已登录的设备上确认（不需要先在网页上生成命令）。

### 丢了设备

账号页 Remove（ADR-0037，不变）。主路径下所有设备都是经账号加入的，这一步能覆盖全部。

### 在别人的电脑上用完

退出登录时勾选"这是公用电脑"：服务端请宿主吊销它，本地忘掉经账号配对的宿主。

## 各部分的改动

### 1. 浏览器确认加入（修订 ADR-0022 §3）

按 RFC 8628（device authorization grant）的形状，加在现有 join token 前面：

1. `pinomad join [origin]`，不带令牌时，宿主调 `POST /api/host-link/start`，带上宿主名、系统、hostId（Ed25519 公钥的指纹）。服务端返回 `{deviceCode, userCode, verifyUrl, interval, expiresAt}`。`deviceCode` 只给宿主，`userCode` 给人看。
2. 宿主打印 `verifyUrl` 和 `userCode`，能开浏览器就打开 `verifyUrl`（不带码），然后按 `interval` 轮询 `POST /api/host-link/poll {deviceCode}`。
3. 用户在已登录的页面上**手动输入** `userCode`。服务端找到请求，显示宿主名、系统、来源 IP 和归属地、hostId 指纹，以及"只确认你自己正在操作的机器"。用户确认后，服务端为这个账号签发一个 join token，绑定到这条请求。
4. 宿主轮询拿到 join token，之后走今天 `join.ts` 的流程：登记、写 `server.json`、安装服务、空闲重启。

保留 `pinomad join <origin> <token>`，给脚本和自动化用。网页上的 Add a host 改成展示那一行命令和"输入短码"入口，生成令牌的旧命令收进"高级"。

防钓鱼（设备码流程的已知弱点：攻击者把自己机器上的码交给受害者，诱导确认）：

- 码只能在页面上手动输入，不提供带码的链接，减少"点一下就确认"。
- 确认页显示来源 IP；来源 IP 和确认者当前 IP 不同时加一行醒目提示。归属地要服务端带 GeoIP 库，是额外的依赖和隐私项，先不做。
- 短码 8 位，取自去掉易混字符的 20 个字母，10 分钟过期，和 join token 一致；输入按账号和 IP 限速，错误多次锁定。
- **新加入的宿主仍然自动配对到所有设备**，并在每台设备上提示一次"新宿主 X 已加入账号"。确认页本身就是这一步的门槛；再让每台设备各点一次，会把今天已经解决的"N 台设备 × M 台宿主"问题带回来。代价要写清楚：被钓鱼时，对方的机器进了账号，它
  - 能经服务端给账号下所有 iPhone 发推送，标题由它决定（ADR-0036）；
  - 作为侧栏里的一台机器，界面内容由它决定，可以伪造"请重新配对另一台宿主"之类的提示；
  - 能读到用户之后主动发给它的内容；
  - 不能进入用户的其他宿主，也拿不到其他宿主上的数据。

  一次性提示和确认页的来源 IP 是针对前两条的主要防线。

`/api/host-link/start` 不需要登录，任何人都能调，所以：

- 按 IP 限速，全局限制同时存在的未确认请求数，过期请求和 join token 用同一轮清理；
- 存下的宿主名、系统和来源 IP 是新的个人数据，隐私政策（#455）加一条，确认或过期后删掉。

这是在 ADR-0022 §3 之前加一种拿到 join token 的方式，原有规则都不变，在 0022 上加修订说明，不另写 ADR。

### 2. 没有宿主时的首页

今天只是账号面板里一行 `No hosts yet. Add one below.`（`account-panel.tsx:371`）。改成：登录后没有宿主时，主区域整屏就是"添加第一台宿主"：

- 那一行命令（带复制按钮）和"输入宿主上显示的短码"的输入框；
- Mac App 上多一个**在终端中运行**，在"终端"里执行这行命令（宿主仍由安装脚本装，App 不带宿主）；
- 一行小字链接到"不用账号的用法"。

iPhone 同理：没有宿主时首页说明"在电脑上运行这行命令"，并给出确认短码的入口。

### 3. 退出登录可以撤销本机（修订 ADR-0037 §3）

ADR-0037 §3 不允许踢当前设备（409 `current_device`），理由是"那是退出登录"。现在把它并进退出登录：`POST /api/logout { revoke: true }` 在同一个事务里删会话、为这台账号设备的每条担保记录写待吊销记录，推送登记随 #489 一起删掉；客户端本地删掉来源是账号的宿主条目，扫码配对的保留。

退出对话框里的勾选框写成"这是公用电脑：让这台设备离开所有宿主"，各端都默认不勾。宿主上的吊销是持久的（ADR-0022 §6），默认勾上的话，自己的浏览器每退出、登录一轮，每台宿主的设备表里就多一条已吊销的旧公钥，几个月下来全是死条目。

不要求重新输入密码：它只撤销发起请求的这台设备自己，拿着被盗会话的人用它只能把自己踢出去。ADR-0037 的 kick 要密码，是因为它能踢掉别的设备。

### 4. 客户端只做控制面（维持 ADR-0003 §2、ADR-0017 §1）

Web、Mac App、iPhone 都只是控制面，不带 Node，也不安装或托管宿主进程。本机也要跑宿主的 Mac 用户，和其他机器一样用安装脚本和 `pinomad up` 装一次。Mac App 只在没有宿主时帮一把：给出命令，提供"在终端中运行"：写一个临时的 `.command` 文件交给"终端"打开执行，用户能看到每一步输出，也不需要向"终端"申请 Apple 事件的控制权限。

不把宿主放进 App 的理由：

- **生命周期分开。** 宿主要常驻、按 ADR-0009 等空闲再重启；App 随时会被退出、被 electron-updater 替换。绑在一起就要处理"App 更新时宿主怎么办""删了 App 宿主服务还在"。
- **只有一份运行时。** Electron 42 自带 Node 24.17，npm 包要求 Node 25，`node-datachannel` 等原生模块要按 Electron 的 ABI 另编一份；App 再打包一份 Node，就和安装脚本、npm 装的宿主并存三套，还要处理两份宿主抢 `~/.pinomad` 的问题。
- **权限归属清楚。** agent 访问 `~/Documents` 等触发的 TCC 弹窗算在宿主进程名下，不会让"打开一个聊天 App"变成"授予它读文件的权限"。
- **各端一个模型。** 宿主可能在没有图形界面的 Linux 上，iPhone 和 Web 本来就带不了宿主；Mac App 也只做控制面，文档和界面只讲一种宿主安装方式。

代价是 Mac 上的新用户要看一次终端。"在终端中运行"和安装脚本把这一步压到点一下按钮、在 App 里输入短码。

### 4.1 Mac App 的"本机宿主"开关

控制面里可以有一个开关，管的是独立安装的宿主服务，不是 App 自带的进程：

- 第一次打开：没有装过宿主时，走"在终端中运行"（安装脚本 + `pinomad up`），装好后开关变成开。
- 之后开或关：对应启动或停止 launchd 服务（`pinomad service install` / `uninstall` 的等价操作），宿主的数据和加入的账号都保留。
- 开关显示服务的真实状态。用户以前用 npm 或安装脚本装过宿主，开关管的就是那一份，不会出现第二份。
- 关掉时提醒：其他设备会连不上这台 Mac，正在跑的任务会按 ADR-0009 等空闲后停。

宿主照样是独立进程、用自己的运行时、自己升级，App 只是它的遥控面板，和"客户端只做控制面"一致。

## 参考：T3 Code

[T3 Code](https://github.com/pingdotgg/t3code)（pingdotgg）和 PiNomad 的形态最接近：机器上跑一个服务端控制 agent，桌面、Web、手机都是客户端，外网访问靠官方的 T3 Connect。以下依据它仓库里的 `docs/user/install.md`、`remote-access.md`、`background-service.md`、`guest-links.md` 和 `docs/internals/t3-connect.md`、`environment-auth.md`（2026-11-01 的 main）。

### 它的上手流程

1. **安装宿主**，二选一：
   - `curl -fsSL https://t3.codes/install.sh | sh`（Windows 用 PowerShell 的 `irm … | iex`），装一个独立的 `t3` 可执行文件到 `~/.local/bin`，不需要预装 Node；
   - 下载桌面 App（Homebrew、winget、deb、AUR、Nix 都有）。桌面 App 自带一个"本机环境"，打开就有服务端在跑，也能在 Settings 里一键装上 `t3` 命令。只想当遥控器的，在 Settings → Environments 关掉 **Local environment**。
2. **让其他设备能连上**：命令行跑 `t3 up`，它问"其他设备怎么连这台机器：T3 Connect、局域网，还是都要"。选 T3 Connect 就登录账号：有浏览器时走 OAuth（PKCE，回调本机端口），SSH 上没有浏览器时打印网址和短码，在任意设备上打开、核对短码一致后批准（Clerk 的 device authorization grant）。然后它把服务装成后台服务。`t3 status` 查看当前选择，带 `--connect` / `--lan` / `--yes` 就不提问。桌面 App 里则是 Settings → Sharing & access 登录并打开 T3 Connect。
3. **其他设备**：登录同一个 T3 Connect 账号，选择机器。app.t3.codes 首页在还没有机器时，登录就会把账号下的机器加进来。
4. **不用账号**：`t3 up --lan` 或 `t3 pair` 出一次性的配对链接或二维码，在接收端 **Add environment** 粘贴或扫码。

### 和 PiNomad 的异同

| | T3 Code | PiNomad 现状 / 本草案 |
|---|---|---|
| 宿主安装 | 独立二进制的安装脚本，或桌面 App 自带 | `npm i -g pinomad`，要先装 Node 25 |
| 宿主接入账号 | 宿主上登录账号本身（OAuth 或设备码） | 现状：网页生成一次性 join token；草案：设备码换 join token |
| 一条命令收拢 | `t3 up` 问怎么连、登录、装服务；`t3 status` 回看 | `host --remote-port`、`service install`、`join`、`pair`、`link` 分开 |
| 设备码确认 | 链接带码，用户核对一致后批准 | 草案：手动输入短码（更防钓鱼） |
| 桌面 App 本机宿主 | 默认开，可关成"只当遥控器" | App 不带宿主；本机宿主用安装脚本装，App 里一个开关启停它 |
| 远程桌面经 SSH | 桌面 App 填 SSH 别名，自动在远端装服务端并转发端口 | 没有 |
| 一台机器多条路 | 明确的"路线"模型：LAN、Tailscale、VPN、公网、SSH、T3 Connect，按顺序先通先用；经 Connect 连上后自动学到 LAN 和 Tailscale 地址 | ADR-0032 的 endpointSet 底层类似，但界面上把"账号"和"配对"讲成两件事 |
| 退出登录 | 只去掉 T3 Connect 这一条路，别的路能到的机器照样保留 | 只去掉服务端担保，配对照样能用（同一个结果） |
| 每台设备的访问 | 宿主上按设备发 session，可带权限范围（scopes），在 Sharing & access 或 `t3 auth session revoke` 吊销 | 宿主设备表按公钥吊销，没有权限范围 |
| 中继看得到什么 | T3 Connect 是"受信任的中介"：经宿主签发一次性引导凭据，客户端拿它直接跟宿主换 session，中继拿不到 session；但流量走每台机器一条的 Cloudflare Tunnel，TLS 在 Cloudflare 边缘终止（按 Cloudflare Tunnel 的工作方式推断，文档没写明） | 服务端担保新设备；流量是 Noise 端到端加密，服务端只转发密文 |
| 账号限额 | 免费账号最多 3 台机器，付费的 T3 Chat 套餐提高到 10 或 100 | 中继按账号限流量和连接数，不限机器数 |

### 对本草案的影响

- **把 `join` 收进一条 `pinomad up`。** T3 Code 最值得学的是"一条命令问清楚怎么连"。建议第一期把 `pinomad join` 做成 `pinomad up` 的一部分：问"经官方服务端 / 只在局域网和 tailnet / 都要"，前者走设备码，后者等价于今天的 `--remote-port`，最后装成服务；`pinomad status` 回看。`join`、`service install` 保留给脚本。这样 A、B、C 三种方式在宿主这边变成同一条命令的三个选项。
- **安装脚本应该进第一期。** T3 Code 的一行命令不需要预装 Node，这是它"一行命令"成立的前提。我们的 `npm i -g pinomad` 先要有 Node 25，对新用户是最大的门槛。待定问题 5 改为第一期的候选：`curl -fsSL https://pinomad.si/install.sh | sh` 下载官方 Node 和 pinomad 包到 `~/.pinomad/runtime`。
- **设备码确认保持手动输入。** T3 Code 用的是 Clerk 托管的设备页，核对短码后批准，更省事。PiNomad 的账号登录后会把新宿主自动配对到所有设备，被钓鱼的代价更大，所以维持手动输入。
- **不跟：桌面 App 自带服务端。** T3 Code 的桌面 App 默认就是一台宿主，"只当遥控器"要手动关。PiNomad 保持客户端和宿主分离（见上文第 4 节），本机宿主也走安装脚本。
- **界面以"机器"为中心，账号只是到达它的一条路。** T3 Code 的路线模型把"账号 vs 配对"的困惑消解掉了：用户看到的是一台台机器，每台下面列出能到达它的路，退出账号只少一条路。PiNomad 底层已经有候选列表（ADR-0032），可以在 Settings → Hosts 里照这个方式呈现，作为第零期"没有宿主时的首页"之后的一项。
- **经 SSH 添加远程宿主**可以作为第二期的候选：桌面 App 填 SSH 别名，经 SSH 在远端跑安装脚本和 `pinomad up`，用户不用登录那台机器。App 只是替用户执行命令，不携带宿主，和"客户端只做控制面"不冲突。
- **按设备的权限范围**（只读、不能开终端等）目前不需要，记下来。

## 分期

**第零期：不改宿主协议，三到四个 PR**

- 修正 `official-server.mdx`、`official-server.zh.mdx` 和 `usage.zh.md` 里"登录后点 Pair"的过时说法。
- 没有宿主时的首页（Web 和 Mac 先做，iPhone 单独一个 PR）。
- 退出登录时撤销本机：服务端 `logout { revoke }` 和 ADR-0037 修订说明；`packages/client` 的登出请求变了，按规则同步 `crates/pinomad-core` 并重新生成对照向量；Web 和 iOS 各一个 PR。

**第一期：一条命令装好宿主并加入账号**

- 服务端：`/api/host-link/start`、`/poll`、确认接口，限速和过期清理，ADR-0022 修订说明。
- 宿主：`pinomad join` 不带令牌时走确认流程，能开浏览器就打开。
- 宿主：`pinomad up` 收拢"怎么连"（官方服务端 / 局域网和 tailnet / 都要）、加入账号和装服务，`pinomad status` 回看。
- 安装脚本 `pinomad.si/install.sh`：下载官方 Node 和 pinomad 包到固定的运行时目录，不要求预装 Node。
- Web 和 Mac：输入短码的确认页，Add a host 改成新流程。
- iOS：输入短码确认（可选，单独 PR）。
- 文档改版：快速上手以账号为主线，"不用账号"单独成页。
- Mac App：本机宿主开关（第 4.1 节），排在 `pinomad up` 和安装脚本之后。

**第二期候选**

- Settings → Hosts 以"机器 + 到达它的路"呈现（账号中继、局域网、tailnet），退出账号只少一条路。
- Mac App 经 SSH 添加远程宿主：填 SSH 别名，自动在远端装宿主并加入账号。

## 待定问题

4. 宿主要求 Node 25 的硬性原因需要核实。如果 24 也能跑，第一期的一行命令门槛会低一些。
5. 公开注册还要不要邀请码，属于 M9 之后的运营决定，但它决定了"在官网注册"这一步的摩擦。
